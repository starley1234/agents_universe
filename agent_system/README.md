# Агентная система

Автономный агент с инструментами: читает и правит файлы, запускает
команды, проверяет результат. Запускается на вашем сервере.

**Зависимостей нет** — только стандартная библиотека Python 3.10+.
`pip install` не нужен для ядра. Навыки `pdf`/`docparse`/`pg_ontology`
(чтение документов, онтология в PostgreSQL) — опциональны, ставятся
по потребности: `pip install -r requirements-optional.txt` или см.
раздел [«Наборы навыков»](#наборы-навыков).

---

**Требования:** Python 3.10+. Работает на Debian с 1 ГБ RAM —
измерено 24 МБ RSS.

**Начните с [OVERVIEW.md](OVERVIEW.md)** — как работает, как пользоваться,
честная оценка и разбор «нужен ли PostgreSQL + pgvector».

Подробно: [ARCHITECTURE.md](ARCHITECTURE.md) — устройство, выбор модели,
экономия токенов. [AUTONOMY.md](AUTONOMY.md) — автономная работа часами.

## Быстрый старт

```bash
cd agent_system
make test                     # 690 проверок, ~32 с
make build-sandbox            # образ песочницы (для sandbox=docker)

export OPENAI_API_KEY=sk-...
python3 -m agent --check      # самопроверка окружения
python3 -m agent "напиши скрипт сортировки и проверь его на тестах"
```

Интерактивный режим — без аргументов:

```bash
python3 -m agent
```

Веб-интерфейс и API:

```bash
make serve                    # http://127.0.0.1:8080/
```

Морда — один HTML-файл на ванильном JS, без сборки и зависимостей.

## Внешние сервисы (MCP)

Веб-поиск, загрузка страниц, картинки, речь — через **ваши MCP-серверы**
(те же, что в LM Studio). У каждого свой лимит частоты:

```json
"search": { "rate_limit": 20 },   // не чаще раза в 20 с
"fetch":  { "rate_limit": 0 }     // безлимитно
```

Недоступный сервер не ломает агента. Подробно — [MCP.md](MCP.md).

## Показ артефакта

Инструмент `present` собирает итог прогона в **одну HTML-страницу**:
сводка, план, выясненные факты, вложенные файлы (картинки вшиты в
base64). Открывается в браузере, самодостаточна.

## Автономный режим

Агент работает часами сам: планирует, копит знания в SQLite, строит
онтологию, рефлексирует, не зацикливается.

```bash
python3 -m agent --auto -P cad_auto --hours 8 "оптимизировать редуктор"
python3 -m agent --auto --resume 3        # продолжить после обрыва
```

Состояние — один файл `agent.db`: память с полнотекстовым поиском,
граф объектов и связей, план, журнал действий. Переживает перезапуск.

Подробно — [AUTONOMY.md](AUTONOMY.md).

## Роли (профили)

```bash
python3 -m agent -P cad       "проверь сборку узла"
python3 -m agent -P marketing "лендинг для редуктора"
python3 -m agent -P research  "выжимка по материалам в папке"
python3 -m agent -P coder     "почини падающий тест"
python3 -m agent -P intake    "разбери скан накладной"
python3 -m agent -P reporter  "собери презентацию по итогам и отправь в MAX"
python3 -m agent -P cert_auditor "проверь комплект документов на соответствие ФАП-21"
```

Профиль = роль + набор навыков + лимит шагов, файл в
`agent/profiles/*.json`. У `cad` 11 инструментов, у `marketing` — 5.

### Авто-выбор профиля (`--auto-route`)

Не хотите указывать роль вручную — пусть система сама решит, каким
профилем выполнять задачу:

```bash
python3 -m agent --auto-route "разбери накладную и вытащи из неё товары"
# роль подобрана автоматически: intake (heuristic; ...)
```

Решение принимается в два шага (`agent/router.py`):
1. **Эвристика** по ключевым словам из `description`/`keywords` каждого
   профиля — бесплатно, мгновенно, без обращения к модели. Срабатывает,
   когда есть однозначный лидер (больше совпадений, чем у любого
   другого профиля).
2. **LLM-фолбэк** — если эвристика не уверена (несколько профилей
   набрали одинаковый счёт или совпадений вообще нет), один короткий
   вызов ОСНОВНОЙ диалоговой модели (отдельного ключа не требуется):
   выбрать одно имя из списка реально существующих профилей. Ответ, не
   совпавший ни с одним именем, игнорируется — тогда берётся лучший
   эвристический вариант.

`--auto-route` нельзя сочетать с `-P/--profile` — если роль указана
явно, роутинг не нужен. То же самое доступно через HTTP API: добавьте
`"auto_route": true` в тело `POST /run` (см. ниже).

**Это НЕ мультиагентный оркестратор.** Выбор происходит ровно один раз,
до старта — дальше работает один обычный `Agent` с выбранным профилем
до конца задачи, никакой передачи управления в процессе работы нет. Это
осознанное ограничение архитектуры (см. `ARCHITECTURE.md`, раздел 4):
один цикл, один набор инструментов на запуск — так надёжнее и дешевле,
а ошибки не прячутся за передачей ответственности между агентами.

Свой профиль под задачу — JSON в `agent/profiles/` с полями `name`,
`description`, необязательным `keywords` (список терминов для точнее
эвристики), `skills`, `max_steps`, `system_prompt`.

## Надёжность и расход

**Повтор при сбое связи.** Сеть моргнула или сервер ответил 503 —
агент подождёт (2, 4, 8 с) и повторит. Восьмичасовой прогон больше не
обрывается из-за одной ошибки. Ошибки настройки (401, 400) не
повторяются: это трата времени.

**Учёт токенов и денег.** После каждого запуска видно, сколько
израсходовано:

```
токенов: 12,480 (вход 11,200, выход 1,280), вызовов: 8  · примерно $0.0024
```

Для локальных моделей — «оплаты нет». Для неизвестных честно пишет
«цена неизвестна», а не выдумывает сумму. В автономном режиме расход
копится в базе по прогону.

## Экономия токенов

```json
"tool_result_limit": 4000,
"keep_last_results": 3
```

Длинные результаты обрезаются, старые сворачиваются в строку.
Измерено на цикле из 8 вызовов: **−74 % контекста**
(15 300 → 3 900 токенов).

## Безопасность

Агент выполняет команды, поэтому изоляция — не опция.

**`sandbox.mode: "auto"`** (по умолчанию) — есть Docker, работаем в
одноразовом контейнере; нет — на хосте с подтверждением опасных команд.
Без демона инструмент не отказывает, а деградирует, честно сообщая об
этом в выводе.

**`"docker"`** — каждая команда в одноразовом контейнере: сеть
выключена, лимиты CPU и памяти, наружу видна только рабочая папка.

**`"confirm"`** — прямой запуск, но опасные команды (`rm -rf`, `mkfs`,
`curl | sh`, fork-бомба и другие) требуют подтверждения оператора.

**`"off"`** — без ограничений, если изолируете сами.

Независимо от режима работают:

- **защита рабочей папки** — путь проверяется после `resolve()`, поэтому
  `..`, абсолютные пути и симлинки наружу отсекаются одинаково;
- **тайм-ауты** — зависшая команда не вешает агента;
- **обрезка вывода** — мегабайтный лог не засоряет контекст.

### Набор `cad`

Проверки, отработанные на реальном проекте планетарного редуктора.
Главный принцип: **не оценивать геометрию на глаз**.

- `scad_collision` — булево пересечение двух тел с **оценкой объёма**.
  Отличает реальное внедрение от касания по плоскости: у сопрягаемых
  деталей пересечение — лист нулевого объёма, и это норма.
- `stl_check` — водонепроницаемость (каждое ребро ровно в двух
  треугольниках) и число связных компонент. Ловит дыры и отвалившиеся
  части, невидимые на рендере.
- `stl_bbox` — реальные габариты и объём, чтобы сверять с расчётом.

### Набор `pdf`

Читает PDF в два шага. **Шаг 1** — классификация КАЖДОЙ страницы
локально, без обращения к модели: по текстовому слою, векторной
графике, таблицам и ключевым словам странице присваивается тип
(`bom_table`, `invoice_financial`, `technical_drawing`, `prose_text`,
`presentation_slide`, `scanned_image`, `blank_page`, `mixed_report`).
Один файл — например, комплект конструкторской документации — обычно
содержит страницы РАЗНЫХ типов (титул, спецификация, чертежи), и
`pdf_classify` разбирает их постранично.

**Шаг 2** — страница рендерится в PNG и распознаётся vision-моделью
с инструкцией, подобранной под тип: для табличных типов — строгий JSON
прямо построчно, для остального — markdown с сохранением структуры.
Пустые страницы не отправляются модели — экономия токенов.

```json
"skills": ["pdf"],
"vision_provider": "openai",
"vision_model": "gpt-4o-mini",
"pdf_dpi": 170
```

Без `vision_*` используется основная модель диалога — навык работает
из коробки, если она умеет в изображения. Требует `pip install pymupdf`.

### Набор `docparse`

Тот же конвейер идей, что у `pdf`, но для Word/Excel/CSV/текста —
и БЕЗ рендера в картинку: `.docx`/`.xlsx` уже дают точный текстовый и
табличный слой, поэтому извлечение (`doc_extract`) детерминированное —
табличные типы сериализуются в JSON прямо из ячеек, без риска, что
модель ошибётся в цифре. Документ Word делится на разделы (между
заголовками), Excel — на листы; классификация (`doc_classify`) — теми
же правилами, что и у `pdf_classify`.

`extract_entities` — третий шаг: берёт уже готовый markdown/JSON (от
`pdf_extract` или `doc_extract`) и текстовой моделью выделяет объекты
предметной области и связи между ними, тут же записывая их в общую
онтологию (`Store.entity`/`relation`, те же таблицы, что у
`note_entity`/`link` из навыка `memory`) — так классифицированный
документ превращается в связанные объекты графа знаний.

Требует `pip install python-docx openpyxl`.

### Набор `pg_ontology`

Онтология в PostgreSQL + pgvector — для тех, кому SQLite (`memory`)
недостаточно: общий доступ из нескольких процессов/машин и, главное,
**поиск по смыслу** через векторное расстояние (`pg_semantic_search`),
а не только по точным словам, как в FTS. Схема похожа на `memory`
(сущности, связи, фрагменты), чтобы инструменты не создавали второй
язык описания графа знаний.

```json
"skills": ["pg_ontology"],
"pg_dsn": "postgresql://user:pass@host:5432/db",
"embedding_provider": "openai",
"embedding_model": "text-embedding-3-small"
```

Подключение к базе ленивое — сборка агента не падает, если Postgres
временно недоступен, ошибка приходит только при реальном вызове
инструмента. Без `embedding_provider` эмбеддинги считаются локальным
детерминированным `hash`-эмбеддером (без сети и ключа) — хуже по
семантике, но работает всегда. Требует `pip install "psycopg[binary]"`
и расширение `vector` на стороне сервера.

### Набор `office`

Создание документов Word/Excel/PowerPoint — симметрично `docparse`
(тот ЧИТАЕТ офисные форматы, этот их СОЗДАЁТ). Никакой модели внутри:
все операции детерминированные, как в `cad_openscad`. Текстовое
содержимое передаётся упрощённым markdown (заголовки `#`/`##`, абзацы,
списки, таблицы `| a | b |`, `**жирный**`/`*курсив*`) — модели пишут
markdown естественно и без ошибок разметки, а разбором и версткой в
docx/pptx занимается код:

- `docx_create`/`docx_append`/`docx_add_table`/`docx_add_image` — Word;
- `xlsx_create`/`xlsx_write_rows`/`xlsx_add_chart` — Excel, включая
  диаграммы (bar/line/pie) по уже записанным данным;
- `pptx_create`/`pptx_add_slide`/`pptx_add_table_slide`/
  `pptx_add_image_slide` — PowerPoint, с заметками докладчика.

```json
"skills": ["office"]
```

Результат `pdf_extract`/`doc_extract` можно почти напрямую передать
сюда, чтобы собрать итоговый отчёт по распознанным документам. Требует
`pip install python-docx openpyxl python-pptx`.

### Набор `messaging`

Связь с внешним миром: email (SMTP для отправки, IMAP для чтения),
Telegram Bot API, MAX Bot API ([dev.max.ru](https://dev.max.ru/docs-api)).
Только стандартная библиотека Python — `smtplib`/`imaplib`/`urllib`,
без внешних зависимостей.

**Инструмент появляется только для НАСТРОЕННОГО канала**: агент не
должен видеть возможность, которой не может воспользоваться. Канал
считается настроенным, если заданы его секреты (см. `.env.example`):

```bash
TELEGRAM_BOT_TOKEN=...
MAX_BOT_TOKEN=...
SMTP_HOST=... SMTP_USER=... SMTP_PASSWORD=...
IMAP_HOST=... IMAP_USER=... IMAP_PASSWORD=...
```

Остальные параметры (порт, TLS-режим, лимит частоты) — в JSON-конфиге,
секция `messaging` (см. `examples/config.messaging.json`):

```json
"skills": ["messaging"],
"messaging": {
  "email": {"smtp_port": 587, "smtp_starttls": true, "from_addr": "bot@example.com"},
  "telegram": {"rate_limit": 1.0},
  "confirm_sends": true
}
```

**Отправка — необратимое действие** (письмо ушло, сообщение увидели —
не отозвать), поэтому `email_send`/`telegram_send_message`/
`telegram_send_file`/`max_send_message` помечены `dangerous=True` и по
умолчанию (`confirm_sends: true`) спрашивают подтверждения оператора
перед реальной отправкой — так же, как `run_command` для опасных
команд. Автономный прогон без оператора должен явно поставить
`confirm_sends: false`, беря ответственность на себя.

Типичный сценарий «входящее фото/документ → анализ → отчёт»: получить
вложение (`email_read`, либо через `agent/webhooks.py` — см. ниже) →
сохранить в workspace → распознать (`pdf_extract`/`doc_extract`,
`extract_entities`) → собрать отчёт (`office`) → отправить обратно
(`telegram_send_file`/`max_send_message`/`email_send`).

#### Приём вложений через Webhook (`agent/webhooks.py`)

`telegram_get_updates`/`max_get_updates` (Long Polling) видят только
ТЕКСТ входящего сообщения — сам файл туда не попадает, только его
описание. Единственный способ реально скачать фото/документ, присланный
боту, — Webhook: платформа сама стучится HTTP POST-ом на наш сервер,
когда пользователь что-то прислал.

`agent/server.py` поднимает два маршрута:

- `POST /webhook/telegram` — секрет проверяется по заголовку
  `X-Telegram-Bot-Api-Secret-Token`;
- `POST /webhook/max` — секрет проверяется по заголовку
  `X-Max-Bot-Api-Secret`.

Маршрут появляется, ТОЛЬКО если в конфиге задан
`messaging.telegram.webhook_secret`/`messaging.max.webhook_secret`
(через переменные окружения `TELEGRAM_WEBHOOK_SECRET`/
`MAX_WEBHOOK_SECRET`, см. `.env.example`) — без секрета мы не можем
отличить платформу от произвольного POST-запроса из интернета, поэтому
тихого «вебхук без проверки» здесь нет: сервер просто не регистрирует
маршрут (404), пока секрет не задан.

Что происходит на каждый входящий запрос:

1. Секрет из заголовка сверяется с настроенным — не совпал → `401`,
   ничего не скачивается и не запускается.
2. Ответ `200 OK` отправляется НЕМЕДЛЕННО, сама обработка уходит в
   фоновый поток — оба API требуют быстрого ответа (MAX жёстко: 30 с,
   иначе до 10 повторных попыток доставки того же события).
3. В фоне: вложение скачивается (`getFile`+загрузка по токену у
   Telegram, прямая ссылка `payload.url` у MAX) и сохраняется в
   `workspace/inbox/<telegram|max>/<чат>/`; имя файла от платформы
   очищается (`_safe_name`), чтобы не выйти за пределы этой папки.
4. Собирается агент с профилем `messaging.webhook_profile` (если задан,
   иначе — тем же, с которым поднят сервер) и получает задачу с текстом
   сообщения и перечнем сохранённых файлов.
5. Ответ агента уходит обратно в тот же чат тем же каналом
   (best-effort: если платформа недоступна, вебхук это уже не блокирует
   — событие было принято на шаге 2).

Зарегистрировать сам вебхук на стороне платформы (сообщить ей внешний
HTTPS-адрес сервера) — отдельный шаг, не выполняется автоматически при
старте (внешний адрес сервера агенту не известен):

```python
from agent.webhooks import register_telegram_webhook, register_max_webhook
register_telegram_webhook(cfg.messaging.telegram, "https://your-domain.com/webhook/telegram")
register_max_webhook(cfg.messaging.max, "https://your-domain.com/webhook/max")
```

Пример конфига — `examples/config.messaging.json` (поля
`messaging.telegram.webhook_secret`/`messaging.max.webhook_secret`/
`messaging.webhook_profile`).

### Набор `rag`

Классический RAG (retrieval-augmented generation) — плюс режим на
онтологии. Решает задачу «документов больше, чем влезает в контекст
модели»: текст индексируется один раз (`rag_index`), а на каждый вопрос
подтягиваются только релевантные фрагменты (`rag_query`), а не всё
хранилище целиком.

- `rag_index(text|path, source, entity_refs)` — режет текст на фрагменты
  по границам абзацев с перекрытием (`rag_chunk_size`/`rag_chunk_overlap`
  в конфиге), считает эмбеддинги и сохраняет. Источником может быть ЛЮБОЙ
  готовый текст — результат `pdf_extract`/`doc_extract`, обычный
  markdown-файл, произвольная строка; сам `rag` документы не парсит.
  Повторная индексация того же `source` заменяет старые фрагменты, а не
  копит дубли. `entity_refs='part:AB-01,assembly:Редуктор'` привязывает
  фрагменты к объектам онтологии — для RAG на онтологии.
- `rag_query(query, top_k, source)` — обычный RAG: гибридный поиск
  (косинусное сходство эмбеддингов + полнотекстовый поиск по словоформам,
  тот же движок, что у `recall`) по всем проиндексированным фрагментам.
  Гибрид нужен потому, что эмбеддинги плохо ловят точные идентификаторы
  (номера деталей, коды ГОСТ), а FTS не понимает синонимы.
- `rag_query_entity(kind, name, query)` — RAG НА ОНТОЛОГИИ: сначала
  фрагменты, явно привязанные к объекту через `entity_refs`, затем (если
  задан `query`) — фрагменты семантически похожих объектов. Точнее
  обычного RAG для вопросов вида «что известно про AB-01»: ответ не
  размывается похожими по тексту, но не связанными фрагментами.
- `rag_stats` — сколько фрагментов и источников проиндексировано.

```json
"skills": ["rag"],
"rag_chunk_size": 1200,
"rag_chunk_overlap": 150,
"rag_top_k": 6
```

**Два бэкенда, один и тот же набор инструментов сверху** — переключаются
той же переменной, что и `pg_ontology`:
- без `pg_dsn` — SQLite (`agent.db`, тот же файл, что у `memory`/
  `docparse`), косинусное сходство считается в памяти; годится для
  одной машины и не требует ничего, кроме самого проекта (эмбеддинги —
  локальным `hash`-эмбеддером без сети и ключа, если `embedding_provider`
  не задан явно);
- с `pg_dsn` — PostgreSQL+pgvector (`store_pg.py`), тот же навык, что
  использует `pg_ontology`, только через ЭТИ инструменты, а не `pg_*`.
  Подключение ленивое — сборка агента не падает при недоступном Postgres.

### Набор `cert_verify`

Валидация и верификация комплекта документов для сертификации
авиационной техники (Росавиация/Авиарегистр, Федеральные авиационные
правила Часть 21 — ФАП-21). Использует терминологию ФАП-21:
Сертификационный базис — набор применимых требований к лётной годности;
Доказательная документация — документы с результатами расчётов,
испытаний, оценок; итог работы — акт о соответствии/несоответствии.

**Главный принцип, ради которого это отдельный код, а не просто промпт
«проверь документы»: модель НЕ МОЖЕТ проставить «соответствует» на
основе выдуманной цитаты.** Тот же приём, что доказательные проверки в
`cad_openscad` («не оценивать геометрию на глаз») — здесь применён к
доказательствам соответствия.

- `checklist_from_text` — разбирает текстовый чек-лист требований (по
  одному пункту на строку) в структуру, чтобы пройти его по порядку.
- `cert_check(requirement, verdict, evidence_source, evidence_quote)` —
  регистрирует вывод по ОДНОМУ пункту требования. Для
  `verdict=compliant/non_compliant` `evidence_source` и `evidence_quote`
  ОБЯЗАТЕЛЬНЫ — без них такой вывод не регистрируется вовсе. Инструмент
  САМ ищет цитату дословно (после нормализации пробелов/регистра) в
  указанном источнике — файле workspace или фрагменте, ранее
  проиндексированном навыком `rag`. **Если цитата не находится — verdict
  принудительно понижается до `needs_review`, что бы ни утверждала
  модель.** Слишком короткая (вырожденная) цитата отклоняется сразу:
  иначе любое слово «находилось» бы в любом документе.
- `cert_report` — итоговый акт: сводка по всем пунктам (сколько
  `compliant`/`non_compliant`/`not_found`/`needs_review`, сколько цитат
  не подтвердилось) и явный вывод о готовности комплекта к подаче.
- `cert_reset` — начать проверку заново для другого комплекта документов.

```json
"skills": ["files", "pdf", "docparse", "rag", "cert_verify", "present"]
```

Профиль `cert_auditor` собирает всё необходимое для этого сценария:
распознавание документов (`pdf`/`docparse`), поиск по большому
комплекту (`rag`), сами проверки (`cert_verify`) и итоговый HTML-отчёт
(`present`). Не требует секретов/внешних сервисов сверх обычной модели.

## HTTP API

```
GET  /health         жив ли сервис (без токена)
GET  /info           конфигурация и список инструментов
POST /run            {"task": "..."} -> результат с трассировкой
POST /run/stream     то же, события построчно (NDJSON)
```

```bash
curl -X POST http://127.0.0.1:8080/run \
  -H "Authorization: Bearer $AGENT_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"task": "перечисли файлы и найди TODO"}'
```

Если `AGENT_API_TOKEN` не задан, сервер **отказывается** слушать
что-либо кроме `127.0.0.1` — чтобы открытый наружу агент не оказался
доступен без пароля.

В запросе можно переопределить `workspace`, `model`, `provider`,
`max_steps`, `skills` — удобно обслуживать несколько проектов одним
сервисом.

`"auto_route": true` (без явного `"profile"`) поручает выбор роли
самому сервису — тот же механизм, что `--auto-route` в CLI (см. раздел
«Авто-выбор профиля» выше):

```bash
curl -X POST http://127.0.0.1:8080/run \
  -H "Authorization: Bearer $AGENT_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"task": "разбери накладную и вытащи товары", "auto_route": true}'
```

В ответе (и в стриме — отдельным событием `route`) появятся поля
`profile` и `route` с объяснением выбора.

## Веб-морда конфигов/логов (дашборд)

`GET /dashboard` — страница поверх того же `agent/server.py` (тот же
токен `AGENT_API_TOKEN`, что и `/run`), без единой сторонней
зависимости — чистый HTML+JS (`agent/web/dashboard.html`), данные через
JSON-эндпоинты `/api/*`, реализованные в `agent/webui.py`. Отдельного
процесса/порта не требуется: `make serve` поднимает и API, и дашборд
сразу.

Разделы дашборда:

- **Обзор** — сколько накоплено (прогонов, фактов памяти, объектов
  онтологии, связей, фрагментов RAG, проверок сертификации) —
  `GET /api/counts`.
- **Профили** — список всех `agent/profiles/*.json` с
  описанием/навыками/лимитом шагов, форма создания и редактирования
  (`description`, `keywords`, `skills`, `max_steps`, `system_prompt`) и
  удаление. Секретов в профиле нет и не может быть — вся форма состоит
  из непривилегированных полей, ключи/пароли по-прежнему только в
  `.env` (см. «Безопасность» выше). Частичное сохранение не стирает
  поля, не показанные в форме. Имя профиля проверяется
  (`^[a-zA-Z][a-zA-Z0-9_-]{0,63}$`) до записи на диск — как и везде в
  системе, путь, пришедший снаружи, не может выйти за пределы своей
  папки.
- **Прогоны** — история `run`/`task`/`event` из `Store` (то же
  хранилище, что использует `memory`/`autorun`): цель, статус, число
  шагов и токенов, план по пунктам, полный журнал событий, а для
  прогонов с навыком `cert_verify` — таблица проверок сертификации.
- **Автономный режим** — запустить (`POST /api/auto/start`: цель,
  профиль, бюджет часов/итераций), остановить (`POST /api/auto/stop`) и
  смотреть живой журнал (`GET /api/auto/stream`, NDJSON — тот же формат,
  что `/run/stream`) прогон `AutoRunner` прямо из браузера. Один
  активный автономный прогон на процесс — второй запуск, пока первый
  идёт, получает явный отказ, а не тихую порчу состояния (два потока не
  должны писать в один `run_id`). Остановка — **кооперативная**:
  `AutoRunner` проверяет флаг между итерациями (`stop_event`), а не
  убивает поток — иначе можно оборвать запись в SQLite на середине.
- **Память** — поиск по `fact` тем же гибридным `recall`, что использует
  инструмент `remember`/`recall` у агента.
- **Онтология** — интерактивный граф (`GET /api/graph`, узлы `entity` +
  рёбра `relation`) на голом `<canvas>` без сторонних JS-библиотек:
  простая force-directed раскладка (отталкивание всех узлов друг от
  друга + пружина по рёбрам + лёгкое стягивание к центру), узлы можно
  перетаскивать мышью, наведение показывает описание объекта во
  всплывающей подсказке, цвет узла зависит от `kind`. В граф попадают
  ТОЛЬКО объекты, у которых есть хотя бы одна связь — изолированные
  объекты (например, ещё не связанные заметки) в графе неинформативны и
  доступны отдельно в табличном виде (переключатель «Показать
  таблицами»/«Показать граф»). Фильтр по типу объекта показывает его
  окрестность — все связи, где этот тип встречается хотя бы с одной
  стороны, а не только рёбра строго между объектами этого типа.

```bash
open http://127.0.0.1:8080/dashboard      # локально, без токена (страница —
                                           # пустая оболочка, данные проверяют
                                           # Authorization в поле "токен")
```

## Как это проверено

Тесты писались по тому же правилу, что и инженерные проверки:
**тест обязан уметь падать**.


```
make test        # 690 проверок (ядро + память + автономия + MCP + pdf + docparse + pg_ontology + office + messaging + router + rag + cert_verify + webhooks + webui)
make test-e2e    # 18 проверок на реальных сокетах
```

Покрыто: изоляция путей (включая симлинки), файловые операции, тайм-ауты
и обрезка вывода, детектор опасных команд, устойчивость цикла к ошибкам
инструментов, лимит шагов, обрезка истории, конфигурация, разбор STL.

Проверка чувствительности — вносили дефекты и убеждались, что тесты их
ловят:

| внесённый дефект | реакция |
|---|---|
| убрана проверка выхода за workspace | 6 падений |
| убрана защита от неоднозначной замены | 1 падение |
| ошибка инструмента роняет цикл | падение с трейсбеком |
| отключена свёртка старых результатов | 1 падение |
| обрезка теряет конец текста | 1 падение |
| цель не подставляется в итерацию | 1 падение |
| рефлексия не пишет в память | 1 падение |
| застой игнорируется | 2 падения |
| повтор при сбое отключён | падение с трейсбеком |
| 401 повторяется как временная ошибка | 2 падения |
| usage не читается из ответа | 4 падения |
| цена берётся по первому совпадению | 2 падения |
| reasoning_content игнорируется | 1 падение |
| пустой ответ завершает задачу | 2 падения |
| очистка пути отключена | 5 падений |
| рассуждение принимается за результат | 2 падения |
| флаг from_reasoning не выставляется | 1 падение |

После восстановления — снова 266/266. Значит «пройдено» здесь означает
работоспособность, а не отсутствие проверок.

Набор `cad` проверен на настоящем OpenSCAD: пересечение 3000 мм³
опознано как коллизия, касание гранью — как норма, разнесённые тела —
как чисто.

Набор `pdf` проверен на сгенерированных PDF всех восьми типов страниц
(59 проверок): классификация не путает BOM с прозой, пустая страница не
отправляется модели, невалидный JSON от модели помечается, а не роняет
цикл. Набор `docparse` — аналогично для Word/Excel/CSV (30 проверок):
значения ячеек в JSON проверены на точное совпадение с исходником.
Набор `pg_ontology` проверен на НАСТОЯЩЕМ Postgres+pgvector — временный
кластер поднимается через `pgserver` прямо в тесте и уничтожается после
(25 проверок): семантический поиск, обход графа, повторная индексация
фрагментов. Набор `office` проверен на реальных python-docx/openpyxl/
python-pptx (50 проверок): вложенные списки, точность данных в таблицах
и диаграммах, заметки докладчика. Набор `messaging` проверен на
НАСТОЯЩИХ сокетах (43 проверки): SMTP-сервер aiosmtpd принимает письмо
и получателей проверяют по факту доставки, самодельный IMAP-сервер
(`tests/fake_imap_server.py`, как `fake_mcp_server.py` для MCP) отвечает
настоящим протоколом IMAP4, HTTP-заглушка обслуживает и Telegram, и MAX
Bot API — включая отказ оператора ДО того, как ушёл сетевой запрос.
Авто-выбор профиля (`agent/router.py`) проверен на 33 сценариях: LLM
НЕ вызывается, когда эвристика уверена (проверяется по счётчику
обращений к сценарной модели), выдуманное или отсутствующее имя от
LLM игнорируется, сбой LLM не роняет решение, а сквозной тест
(`test_e2e.py`) проводит `POST /run` с `auto_route` через настоящий
HTTP-стек от запроса до выполненной задачи. Набор `rag` проверен на
43 сценариях на ОБОИХ бэкендах: SQLite (переиндексация заменяет фрагменты,
а не копит дубли; фильтр по source; RAG на онтологии не смешивает
посторонние документы) и НАСТОЯЩИЙ PostgreSQL+pgvector (тот же сценарий
через `build_agent`, включая ленивое подключение — сборка агента не
падает при недоступном DSN). Набор `cert_verify` проверен на 47
сценариях: реальная цитата принимается, ВЫДУМАННАЯ цитата принудительно
понижает verdict до `needs_review` (и это видно и в возвращаемом тексте,
и в самой базе — модель не может «переспорить» проверку), вырожденно
короткая цитата отклоняется, `compliant`/`non_compliant` без
доказательства не регистрируется вовсе. Приём вложений через Webhook
(`agent/webhooks.py`) проверен на 41 сценарии на реальном HTTP-стеке:
поднимаются настоящий `agent/server.py`, фейковые Telegram/MAX API и
фейковая LLM (та же схема, что в `test_e2e.py`) — запрос без секрета или
с неверным секретом отклоняется `401` и вложение при этом НЕ скачивается
(проверено по факту отсутствия обращения к `getFile`), верный секрет
даёт мгновенный `200` (обработка реально уходит в фон — таймер в тесте
это подтверждает), файл вложения реально долетает до диска побайтово,
имя файла от платформы обезврежено от `../`, а без настроенного
`webhook_secret` маршрут не регистрируется вовсе (`404`, а не «принял и
не глядя отклонил»). Веб-морда конфигов/логов (`agent/webui.py`,
`agent/web/dashboard.html`) проверена на 56 сценариях через настоящий
HTTP-стек `agent/server.py`: `/api/*` без токена отклоняются так же, как
`/run`; числа на странице «Обзор» и списки прогонов/памяти/онтологии
сверяются с тем, что реально записано в `Store` (а не с заглушкой);
запись/чтение/удаление профиля происходит на настоящей файловой системе,
недопустимое имя (`../evil`, начинается с цифры, пустое) отклоняется до
записи на диск; частичное сохранение профиля не стирает поля, которых
не было в запросе; автономный прогон запускается и реально доводится до
конца через тот же `AutoRunner`, второй запуск, пока первый идёт,
получает явный отказ (а не тихую порчу состояния в одном SQLite-файле),
кнопка «Стоп» реально прерывает многошаговый прогон РАНЬШЕ конца плана
(проверено по `stopped_by == "stopped"`, а не просто по факту остановки
процесса), а `GET /api/auto/stream` отдаёт настоящие NDJSON-события до
события `done`. Всего у веб-морды 67 проверок (56 базовых + 11 на
`GET /api/graph`/`Store.graph_data`): изолированный объект без единой
связи не попадает в узлы графа (граф информативен только по связям, а
не по каждому объекту в базе), рёбра всегда ссылаются на реально
существующие id узлов, фильтр по типу объекта возвращает его
ОКРЕСТНОСТЬ (обе стороны связи), а не только объекты этого типа, пустая
база не роняет построение графа — отдаёт пустые списки, а не исключение.

## Структура

```
agent/
  core.py           цикл «модель -> инструменты -> модель»
  build.py          сборка агента из конфига
  config.py         конфигурация: файл + окружение + CLI
  router.py         авто-выбор профиля под задачу: эвристика + LLM-фолбэк
  cli.py            командная строка
  server.py         HTTP API + вебхуки Telegram/MAX (POST /webhook/*)
                    + дашборд (GET /dashboard, /api/*)
  webhooks.py       приём вложений через Webhook: проверка секрета,
                    скачивание файла, фоновый прогон агента, ответ в чат
  webui.py          веб-морда конфигов/логов: CRUD профилей, управление
                    автономным прогоном (AutorunManager), выборки для
```
