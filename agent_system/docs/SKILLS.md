# Навыки: документы, RAG, онтология, верификация, fetch

Четыре новых агента и пять навыков. Всё на стандартной библиотеке —
обязательных зависимостей по-прежнему нет.

## Агенты

```bash
python3 -m agent -P docs   "разбери договоры из папки in/ в JSON"
python3 -m agent -P rag    "проиндексируй docs/ и найди требования к материалам"
python3 -m agent -P verify "проверь комплект в ev/ против требований в req/"
python3 -m agent -P onto   "построй онтологию изделия по документам"
```

| профиль | навыки | инструментов |
|---|---|---|
| `docs` | files, documents, memory, present, fetch | 24 |
| `rag` | files, documents, rag, memory, present | 27 |
| `verify` | files, documents, verify, rag, memory, present | 32 |
| `onto` | files, documents, pg, memory, present | 30 |

## 1. Документы (`documents`)

Читает **PDF, Word .docx, Excel .xlsx, CSV, txt, md** → Markdown или JSON.

| инструмент | что делает |
|---|---|
| `doc_read` | документ → текст в Markdown |
| `doc_to_json` | структура: класс, разделы, сущности |
| `doc_to_markdown` | конвертация с сохранением заголовков и таблиц |
| `doc_classify` | тип документа + найденные сущности |
| `doc_link` | документ, разделы и сущности → граф знаний |

**Классы:** нормативный, технический, договор, отчёт, заявка, переписка.
Неопознанный помечается «прочее», а не подгоняется под ближайший.

**Сущности:** даты, номера документов, ГОСТ, ФАП, суммы, размеры,
проценты, email, URL. Только однозначно распознаваемое — догадки в
структурированные данные не попадают.

### Как разбираются форматы

Всё на stdlib: `docx`/`xlsx` — это ZIP с XML, `pdf` — потоки zlib.
Если в системе есть `python-docx`, `openpyxl` или `pypdf` — они
используются, качество выше. Нет — работает резервный путь.

**Границы честно:** собственный PDF-парсер не читает сканы (нужен OCR)
и может путать порядок колонок в сложной вёрстке. Об этом пишется прямо
в выводе. Формат `.doc` не поддержан — подсказывается конвертация.

## 2. RAG (`rag`)

Два режима поиска, и оба нужны:

| инструмент | стратегия |
|---|---|
| `rag_search` | по словам во фрагментах — «где про это написано» |
| `rag_search_ontology` | через граф: объект → документы → фрагменты |
| `rag_answer` | контекст для ответа: фрагменты + факты из памяти |
| `rag_index` | нарезать документы и занести в граф |
| `rag_status` | что проиндексировано |

Поиск через граф находит то, чего нет во фрагменте дословно: раздел про
«предельные отклонения» не содержит слова «ФАП», но связан с ним через
документ.

**Граница:** поиск лексический. Словоформы ловятся стеммингом
(«щека» → «щекой»), но перефразированный смысл без общих слов — нет.
`rag_status` говорит об этом прямо. Семантика — в навыке `pg`.

## 3. Онтология в PostgreSQL (`pg`)

Для случая, когда SQLite не хватает: **агенты на разных машинах** или
**семантический поиск на десятках тысяч записей**.

```json
"pg_dsn": "postgresql://agent:пароль@host:5432/onto",
"embed_url": "http://GPU:1234/v1",
"embed_model": "text-embedding-nomic-embed-text-v1.5",
"embed_dim": 768
```

| инструмент | что делает |
|---|---|
| `pg_status` | состояние базы, сколько записей с векторами |
| `pg_add_entity`, `pg_link` | строить граф |
| `pg_query`, `pg_neighbours` | разбираться: обход графа на глубину 1-3 |
| `pg_add_chunk` | фрагмент с вектором и привязкой к объекту |
| `pg_semantic_search` | **поиск по смыслу** через pgvector |
| `pg_build_index` | ivfflat (нужен от ~1000 записей) |

Эмбеддинги считает ваша локальная модель через `/v1/embeddings` —
отдельный сервис не нужен, токены бесплатны.

**Устойчивость:** `psycopg` не обязателен. Нет библиотеки или БД
недоступна — навык сообщает причину в `pg_status`, остальная система
работает. Проверено тестом.

Нужен ли PostgreSQL вообще — с замерами в [OVERVIEW.md](OVERVIEW.md).
Короткий ответ: при одном агенте на одной машине не нужен.

## 4. Валидация и верификация (`verify`)

Для подготовки к сертификации (ФАП Росавиации и подобное).

**Различение строгое:**
- **валидация** — тот ли документ: комплектность, реквизиты, форма;
- **верификация** — верно ли по существу: требование ↔ доказательство,
  согласованность чисел.

| инструмент | проверяет |
|---|---|
| `check_completeness` | все ли обязательные документы есть |
| `check_requisites` | номер, дата, подпись, исполнитель |
| `verify_requirements` | карта «требование → чем закрыто» |
| `cross_check` | расхождения в числах между документами |
| `audit_report` | сводный отчёт в Markdown |

### Главное ограничение

**Инструмент не выносит заключение о соответствии.** Он находит
формальные пробелы и готовит материал эксперту. Решение принимает
уполномоченный орган. Эта оговорка стоит в каждом отчёте — и проверяется
тестом, чтобы её нельзя было случайно убрать.

### Два дефекта, найденные при разработке

Оба были опаснее отсутствия проверки, потому что создавали ложную
уверенность.

**1. Терялись короткие требования.** Регулярка требовала ≥15 символов до
слова-маркера. «Не допускается…» (4 символа) и «Изделие должно…» (12) не
находились: из четырёх требований видели одно, а покрытие показывали
100 %. Исправлено разбором по предложениям.

**2. Любой протокол «закрывал» любое требование.** Бонус за слово
«протокол» сам перекрывал порог, и климатические испытания считались
закрытыми протоколом нагрузки. Теперь бонус в порог не входит, нужно
совпадение половины ключевых слов, а пограничные случаи идут в
отдельную категорию **«спорно, требует эксперта»** и в покрытие не
засчитываются.

На том же примере: было «100 %», стало честные «25 %».

## 5. Загрузка страниц (`fetch`)

| инструмент | что делает |
|---|---|
| `fetch_url` | страница → текст (или сохранить файлом) |
| `fetch_links` | собрать ссылки |

**Защита от выхода во внутреннюю сеть.** По умолчанию блокируются
localhost и приватные диапазоны: иначе агент из песочницы дотянется до
роутера или облачных метаданных (169.254.169.254). Имя резолвится перед
проверкой — `my.host`, указывающий на 127.0.0.1, тоже отсекается.
Снимается флагом `fetch_allow_private`.

Если у вас настроен MCP-сервер загрузки — он даст лучший разбор, тогда
этот навык можно не подключать.
