# Задание: дискуссия двух моделей с арбитром и исполнителем

> **Состояние: работает. Разбор ведётся ОДНОЙ веткой.**
>
> Ветвление решено не делать: комбинаторный взрыв и двойной расход не
> окупают пользы. Если обе позиции верны при разных условиях, арбитр
> обязан завершить разбор и назвать оба условия в итоге — это дешевле
> и понятнее человеку, чем две параллельные ветки.
>
> По итогам каждого разбора пишется **протокол** — статья с ходом
> рассуждения, проверенными фактами и расхождениями.
>
> ```bash
> agent --debate "нужен ли нам PostgreSQL или хватит SQLite"
> agent --debate --rounds 8 --max-usd 2 --models qwen3-coder,devstral
> agent --debates                  # список разборов
> agent --debate --resume 3        # продолжить
> agent --protocol 3               # пересобрать протокол
> agent --protocol 3 --summarize   # с пересказом моделью
> ```
>
> Не сделано: вкладка в веб-интерфейсе.
> Проверок: 89 в `tests/test_debate.py`, 12 диверсий.

## Решение: делать здесь, отдельным модулем

Отдельный проект пришлось бы начинать с копирования того, что уже
работает и покрыто тестами.

| слой | строк | пригодность для дискуссии |
|---|---|---|
| `llm/` — 9 провайдеров, повтор при сбое, учёт денег | 784 | **100 %** |
| `tools/` — файлы, shell, python, снимки, вопросы | 2083 | **100 %**, нужны исполнителю |
| `skills/` — документы, RAG, verify, comms | 3144 | **100 %**, нужны исполнителю |
| `core.py` — цикл «модель → инструменты → модель» | 284 | **100 %**, это и есть исполнитель |
| `webio.py` — вопрос человеку с ожиданием ответа | 134 | **100 %** |
| `vectors.py` — поиск по смыслу | 193 | **100 %** |
| `store.py` — SQLite | 494 | **80 %**, добавить три таблицы |
| `server.py` — HTTP и веб | 356 | **90 %**, добавить поток дискуссии |
| `dispatch.py` — выбор роли по тексту | 189 | **50 %**, пригодится исполнителю |
| `autorun.py` — автономный цикл | 419 | **0 %**, у дискуссии свой цикл |

Переиспользуется около **90 %**. Написать надо цикл дискуссии — по
оценке 400–500 строк плюс тесты. Отдельный проект означал бы либо
копию 6600 строк, либо зависимость от этой системы как библиотеки —
и то и другое дороже одного нового модуля.

**Вывод:** новый модуль `agent/debate.py` + таблицы в `store.py` +
команда `--debate`. Автономный режим при этом не трогаем: у него другой
цикл, смешивать их в одном файле нельзя.

## Что строим

```
              вопрос человека
                     │
         ┌───────────▼───────────┐
         │      Дискуссия        │  круг: A говорит → B отвечает
         └──┬─────────────────┬──┘
            │                 │
      ┌─────▼─────┐     ┌─────▼─────┐
      │ Сторона A │     │ Сторона B │   разные модели и/или роли
      └───────────┘     └───────────┘
                  │
        правила-триггеры (не модель!)
                  │
         ┌────────▼────────┐
         │     Арбитр      │  продолжить · ветвление ·
         └────┬───────┬────┘  исполнитель · завершить
              │       │
     ┌────────▼──┐  ┌─▼──────────────┐
     │ Ветвление │  │  Исполнитель   │  существующий Agent
     │ (до 2)    │  │  с инструментами│ + build_agent()
     └───────────┘  └────────────────┘
```

**Ключевое разделение:** *когда* звать арбитра решают **правила**,
*что делать* решает **модель**. Правила дёшевы, воспроизводимы и
проверяются тестами; суждение правилами не заменить. Отдавать модели
и то и другое — значит получить дискуссию, которая никогда не
кончается, потому что «ещё один круг» всегда выглядит разумно.

## Четыре роли

| роль | модель | что может | что запрещено |
|---|---|---|---|
| **Сторона A** | своя | довод, вопрос оппоненту, запрос факта | звать инструменты, объявлять итог |
| **Сторона B** | **другая** | то же | то же |
| **Арбитр** | сильная | одно из четырёх решений | вести спор, добавлять доводы |
| **Исполнитель** | любая с инструментами | всё из `tools/` и `skills/` | участвовать в споре |

Стороны **не имеют инструментов намеренно.** Их дело — рассуждать;
всё, что требует проверки, уходит исполнителю. Иначе дискуссия
превращается в две параллельные работы без спора.

Стороны различаются **моделью, промптом или обоими**. Одинаковые модель
и промпт дают монолог в двух лицах — при старте это должно быть
предупреждением, а не молчаливым согласием.

---

## Кто говорит следующим

Ход строго по очереди: A → B → A → B. После каждого **полного круга**
проверяются триггеры арбитра — в этом порядке, до первого сработавшего:

| триггер | как меряется |
|---|---|
| запрошен факт | в реплике маркер `[ФАКТ?]` или явный запрос проверки |
| топтание | подпись довода повторилась ≥ 2 раз |
| согласие | обе стороны согласны И ни одна не внесла нового довода |
| каждые N кругов | принудительно, умолчание N = 3 |
| бюджет на исходе | потрачено ≥ 80 % денег или времени |

**Подпись довода** — от нормализованного текста: слова приводятся к
основам (уже есть `Store._stem`), служебные отбрасываются, остаток
сортируется и хешируется. Так «ресурсов не хватит» и «не хватит
ресурсов» дают одну подпись, а «ресурсов хватит» — другую. Это тот же
приём, что ловит зацикливание в `autorun._sig`.

## Протокол арбитра

Арбитр получает: вопрос, сжатую историю кругов, последние 4 реплики
целиком, причину вызова. Отвечает **только JSON**:

```json
{
  "решение": "продолжить | ветвление | исполнитель | завершить",
  "почему": "одной фразой",
  "вопрос": "что проверить — только для решения «исполнитель»",
  "варианты": ["ветка 1", "ветка 2"],
  "итог": "ответ на исходный вопрос — только для «завершить»"
}
```

Разбор защитный, как в `autorun._reflect`: берём первый `{` и последний
`}`, терпим обёртку из текста. Не разобралось — **не падаем**: считаем
«продолжить», пишем в журнал `arbiter_unparsed`. Три таких подряд —
принудительное завершение: арбитр, который не умеет отвечать по
протоколу, не сможет и остановить спор.

**Ограничение на «продолжить».** Подряд не более трёх раз. После
третьего арбитру в промпте прямо сообщается, что этот вариант больше
недоступен, и он обязан выбрать из трёх остальных. Без этого
арбитр-соглашатель растянет спор до упора в бюджет.

## Одна ветка вместо ветвления

Ветвление было в первом наброске задания и **сознательно отброшено**.
Причина: даже глубина 2 удваивает расход и время, а результат человеку
всё равно надо сводить руками. Развилку дешевле описать словами.

Поэтому арбитру в промпте прямо сказано: обе позиции верны при разных
условиях — **завершай разбор** и назови в итоге оба условия и что
делать в каждом.

Решение «ветвление» из протокола убрано. Если чужая или старая модель
всё же его пришлёт, оно трактуется как «продолжить»: разбор не падает
и не объявляет согласия, которого не было.

## Исполнитель

Вызывается только по решению арбитра, с конкретным вопросом.

1. Профиль выбирается `dispatch.choose_profile()` по тексту вопроса —
   «проверь STL» уйдёт в `cad`, «найди в документах» в `rag`.
2. Запускается обычный `build_agent()` + `agent.run()` — новый код не
   нужен.
3. Результат возвращается в дискуссию **отдельной репликой с ролью
   `инструмент`**.

Правило для сторон, прописанное в промпте: **факт от исполнителя —
единственное, что считается проверенным.** Своё непроверенное
помечать `[ГИПОТЕЗА]`. Это прямое продолжение принципа «не выдавать
непроверенное за проверенное», на котором стоит вся система.

Пределы: не более 5 вызовов исполнителя на дискуссию, `max_steps` = 12.

## Хранение

Три новые таблицы, остальное переиспользуется (`fact` для памяти,
`event` для журнала):

```sql
CREATE TABLE IF NOT EXISTS debate(
  id INTEGER PRIMARY KEY,
  question TEXT NOT NULL,
  status TEXT DEFAULT 'active',   -- active|done|no_consensus|budget|stuck
  model_a TEXT, model_b TEXT, model_arbiter TEXT,
  rounds INTEGER DEFAULT 0,
  cost REAL DEFAULT 0,
  verdict TEXT,
  started REAL, finished REAL
);

CREATE TABLE IF NOT EXISTS branch(
  id INTEGER PRIMARY KEY,
  debate_id INTEGER NOT NULL,
  parent_id INTEGER,              -- NULL = основная ветка
  assumption TEXT,                -- при каком предположении идём
  status TEXT DEFAULT 'active',
  verdict TEXT, created REAL
);

CREATE TABLE IF NOT EXISTS turn(
  id INTEGER PRIMARY KEY,
  debate_id INTEGER NOT NULL,
  branch_id INTEGER,
  round INTEGER,
  role TEXT NOT NULL,             -- a|b|арбитр|инструмент
  model TEXT,
  text TEXT NOT NULL,
  sig TEXT,                       -- подпись довода: ловим топтание
  tokens INTEGER DEFAULT 0,
  cost REAL DEFAULT 0,
  created REAL
);
CREATE INDEX IF NOT EXISTS ix_turn_debate ON turn(debate_id, round);
CREATE INDEX IF NOT EXISTS ix_turn_sig ON turn(debate_id, sig);
```

## Остановка и деньги

Дискуссия останавливается по **любому** из условий:

| условие | статус | что в итоге |
|---|---|---|
| арбитр сказал «завершить» | `done` | его вердикт |
| исчерпаны круги (умолчание 12) | `no_consensus` | позиции сторон |
| исчерпан `--max-usd` | `budget` | позиции + сколько потрачено |
| исчерпано время | `budget` | то же |
| топтание 3 круга подряд | `stuck` | «согласия не достигнуто» + причина |

**Отсутствие согласия — законный результат**, а не ошибка. Итог
обязан честно сказать: «стороны не сошлись, вот позиция каждой, вот в
чём именно расхождение». Выдавать за вердикт мнение того, кто говорил
последним, нельзя.

**Расход растёт квадратично.** Каждый круг обе стороны получают всю
историю: 12 кругов по 400 токенов реплики дают около 120 тысяч
токенов только на вход. Поэтому свёртка обязательна: в контекст идут
вопрос, однострочные итоги прошлых кругов, последние 4 реплики
целиком и все факты от исполнителя. Механизм есть — `core._compact`.

Умолчания: `rounds = 12`, `max_usd = 0` (без предела), `max_minutes = 30`.

## Протокол разбора

Вердикт арбитра — одна-две фразы: «хватит SQLite». Через неделю по нему
не понять, почему так решили, что проверяли и с чем не согласилась
вторая сторона. Поэтому после каждого разбора пишется файл
`протокол-разбора-N.md`.

Разделы:

| раздел | что в нём |
|---|---|
| шапка | вопрос, итог, модели, круги, расход |
| Заключение | вердикт арбитра дословно |
| **Что проверено инструментами** | единственное, чему можно верить без оговорок |
| Ход разбора | связный пересказ — **только** с `--summarize` |
| Позиции сторон | итоговая позиция и все доводы по кругам |
| В чём разошлись | реплики с явным возражением |
| Непроверенные допущения | всё, что стороны пометили `[ГИПОТЕЗА]` |
| Решения арбитра | когда и почему вмешивался |

Три правила, ради которых он такой:

**Не добавляет выводов, которых не было.** По умолчанию собирается из
записей без участия модели: нечему выдумывать. Пересказ моделью — по
явной просьбе `--summarize`, и он не заменяет разделы, а добавляется.

**Не превращает расхождение в согласие.** Не сошлись — так и написано,
с позицией каждой стороны. Это проверяется тестом и диверсией.

**Проверенное отделено от рассуждений.** Раздел «Что проверено» — то,
что получено инструментами. Если проверок не было, стоит прямая
пометка: «разбор шёл только рассуждениями, все утверждения требуют
проверки». Плюс дисклеймер: это не экспертное заключение.

Сбой модели при пересказе не ломает протокол — он соберётся из записей,
и это честнее выдуманного текста.

## Как это проваливается

Разделы выше описывают, что строить. Этот — что сломается, если
строить наивно. Каждый пункт наблюдался в подобных системах.

**1. Поддакивание.** Модели соглашаются на первом ходу: «Отличная
мысль, полностью согласен». Дискуссии нет, деньги потрачены.
*Лечение:* разные промпты с разными критериями оценки; арбитру
запрещено принимать согласие раньше второго круга; сторона обязана
в первом ходу назвать хотя бы одно возражение.

**2. Топтание.** Те же доводы другими словами до упора в лимит.
*Лечение:* подпись довода по основам слов, повтор → арбитр, три
повтора → остановка.

**3. Выдуманные факты.** Обе модели уверенно ссылаются на
несуществующее — и подтверждают друг друга.
*Лечение:* факты только от исполнителя, остальное `[ГИПОТЕЗА]`.

**4. Арбитр-соглашатель.** Всегда «продолжить», потому что так
безопаснее.
*Лечение:* не более трёх «продолжить» подряд.

**5. Дрейф темы.** К десятому кругу спорят не о том, о чём спросили.
*Лечение:* исходный вопрос подставляется в каждый ход заново, из базы,
а не из истории — как `WORKER` в автономном режиме.

**6. Монолог в двух лицах.** Одна модель играет обе стороны.
*Лечение:* при совпадении модели и промпта — предупреждение при
старте; в отчёте видно, чем стороны различались.

**7. Взрыв ветвления.** Три уровня по две ветки — восемь дискуссий.
*Лечение:* глубина 2, ветки последовательно, бюджет делится.

## Что проверять тестами

Как везде в проекте: **тест обязан уметь падать**, каждая критичная
проверка подтверждается диверсией.

| проверка | диверсия, которая обязана её уронить |
|---|---|
| поддакивание распознаётся | две одинаковые модели, обе соглашаются сразу |
| топтание распознаётся | сторона повторяет довод другими словами |
| подпись довода устойчива к перестановке слов | «не хватит ресурсов» = «ресурсов не хватит» |
| числа в доводе значимы | «3 сервера» и «30 серверов» слились бы в одно |
| исполнитель всегда получает инструменты | тема не распознана → приходит без `run_python` |
| арбитр не может тянуть вечно | арбитр всегда отвечает «продолжить» |
| нечитаемый ответ арбитра не роняет | арбитр возвращает мусор вместо JSON |
| предел кругов срабатывает | стороны спорят бесконечно |
| предел денег срабатывает | считаем на реальной цене через `price_of` |
| «не сошлись» — законный итог | итог не выдаёт мнение последнего за вердикт |
| исполнитель зовётся с нужным профилем | вопрос про STL → профиль `cad` |
| факт исполнителя попадает в контекст сторон | ответ инструмента теряется |
| незнакомое решение арбитра не роняет разбор | модель шлёт «ветвление», которого больше нет |
| протокол не превращает расхождение в согласие | «не сошлись» подменяется бодрым итогом |
| протокол отмечает отсутствие проверок | пометка убрана — читатель решит, что подтверждено |
| «принимаю, но…» не считается спором | в расхождения попадает согласие с уточнением |
| дисклеймер на месте | убран — протокол выглядит как заключение эксперта |
| сбой модели не ломает протокол | пересказ падает вместе со всем документом |
| свёртка держит контекст | 12 кругов не дают линейного роста запроса |
| дискуссия переживает перезапуск | `--resume` по номеру |

Проверять на **заглушках-моделях с заданным нравом** (как в
`tests/test_smoke.py`): соглашатель, повторюшка, выдумщик,
арбитр-соглашатель. От системы требуется разное поведение на каждом.

## Интерфейс

```bash
agent --debate "нужен ли нам PostgreSQL или хватит SQLite"
agent --debate "…" --rounds 8 --max-usd 2 --models qwen3-coder,devstral
agent --debate --resume 3        # продолжить дискуссию
agent --debates                  # список, как --runs
```

В вебе — третья вкладка «Дискуссия»: реплики сторон разными цветами,
решения арбитра врезками, вызовы исполнителя раскрываются как вызовы
инструментов, ветки — вложенным списком. Поток тот же NDJSON, события
`turn`, `arbiter`, `branch`, `executor`, `verdict`.

Конфигурация:

```json
"debate": {
  "model_a": "qwen3-coder-30b",
  "model_b": "devstral-small-2:22b",
  "model_arbiter": "devstral-small-2:22b",
  "prompt_a": "Ты сторонник простых решений…",
  "prompt_b": "Ты сторонник запаса прочности…",
  "rounds": 12,
  "arbiter_every": 3,
  "max_branch_depth": 2,
  "max_executor_calls": 5,
  "max_minutes": 30
}
```

## Этапы

Каждый заканчивается проверяемым результатом, не «написан модуль».

**Сделано (1–3).** Ниже отмечено, что именно.

1. **Ядро без арбитра** — две модели, N кругов, хранение реплик,
   свёртка контекста, предел кругов и денег. Результат: дискуссия
   идёт и честно останавливается. Тесты: пределы, свёртка, хранение.
   ✅ сделано
2. **Арбитр** — триггеры, протокол JSON, защитный разбор, лимит
   «продолжить», распознавание поддакивания и топтания. Результат:
   дискуссия завершается по существу, а не по лимиту. ✅ сделано
3. **Исполнитель** — вызов `build_agent`, выбор профиля, факт в
   контексте сторон. Результат: спорный факт проверяется, а не
   додумывается. ✅ сделано
4. **Протокол** — итоговая статья по разбору. ✅ сделано
5. **Веб** — вкладка «Разбор» с репликами и протоколом. ⬜ не сделано

Первые два этапа дают работающую систему; третий делает её полезной;
четвёртый — удобной. Если время кончится после второго, это уже не
черновик.

## Что делать НЕ надо

- **Ветвление.** Отброшено осознанно, см. раздел выше.
- **Больше двух сторон.** Три участника дают шесть пар связей,
  дискуссия рассыпается, а стоимость растёт втрое.
- **Свободный обмен «все со всеми».** Очередь ходов должна быть
  предсказуемой, иначе воспроизвести и отладить прогон невозможно.
- **Отдавать моделям решение, когда звать арбитра.** Они будут звать
  его или всегда, или никогда.
- **Давать сторонам инструменты.** Спор превратится в две параллельные
  работы.
- **Показывать «уверенность» в процентах.** Модели её выдумывают;
  число выглядит убедительно и не значит ничего.

## Что выяснилось при реализации

Три вещи, которых не было в задании и которые нашлись только на
работающем коде.

**Числа выпадали из подписи довода.** Основа слова отбрасывает цифры,
поэтому «аспект 3» и «аспект 4» давали одну подпись, а спор о величине
объявлялся топтанием. Теперь числа берутся целиком.

**Синонимы подпись не ловит.** «Справится с нагрузкой» и «нагрузка по
силам» — разные подписи, хотя мысль одна. Для этого нужны эмбеддинги,
а они не всегда настроены. Такое топтание ловит второй рубеж — арбитр,
которого зовут каждые N кругов. Записано как признанная граница, а не
скрыто.

**Исполнитель приходил без инструментов.** Живой прогон: арбитр просит
посчитать `300000 / 5000`, тема не распознаётся диспетчером, профиль не
выбирается — и агент отвечает «инструмента run_python нет». Набор для
проверки фактов теперь гарантированный (`files` + `python`), независимо
от распознавания темы.

Все три закрыты тестами с диверсиями.
