# Обзор: как работает, как пользоваться, и нужен ли PostgreSQL + pgvector

## Часть 1. Как это работает

### Схема

```
        задача / цель
             │
    ┌────────▼────────┐
    │  Agent (ядро)   │  цикл: модель → инструменты → модель
    └───┬─────────┬───┘
        │         │
   ┌────▼───┐  ┌──▼────────────────────────────┐
   │  LLM   │  │        Инструменты            │
   │драйвер │  │ files · shell · cad · memory  │
   └────────┘  │ present · MCP-серверы         │
   9 провай-   └──┬──────────────┬─────────────┘
   деров          │              │
              ┌───▼────┐    ┌────▼──────┐
              │Workspace│   │  SQLite   │
              │изоляция │   │ память,   │
              │ путей   │   │ онтология,│
              └─────────┘   │ план      │
                            └───────────┘
```

Ядро не знает ни про провайдера, ни про предметную область. Провайдер —
сменный драйвер, область — профиль (JSON из четырёх полей).

### Два режима

**Разовая задача.** Один цикл: модель просит инструменты, получает
результаты, отвечает. Останов — когда модель ответила текстом без
вызовов, или по лимиту шагов.

**Автономный прогон.** Часы работы без человека:

```
цель → планировщик → 3-7 пунктов в базу
  ↓
┌─ взять пункт
│  контекст = цель + пункт + память по теме + последние действия
│  агент работает инструментами
│  plan_done / plan_fail
│  рефлексия → факты в память
│  плохо идёт? → перепланирование
└─ повторить
  ↓
останов: план выполнен | время | лимит | застой
```

Ключевое: **цель подставляется в каждую итерацию заново из базы**, а не
тащится в истории. Иначе через час агент работает вслепую.

### Что хранится

Один файл SQLite: факты с полнотекстовым поиском, граф объектов и
связей, план, журнал действий. Переживает перезапуск процесса и сервера.

## Часть 2. Как пользоваться

### Установка

```bash
cd agent_system
make test           # 266 проверок, ~30 с
make build-sandbox  # образ песочницы (если нужен docker-режим)
```

Зависимостей нет — только Python 3.10+.

### Подключение модели

```bash
# ваш GPU-сервер с LM Studio
python3 -m agent -p lmstudio -m devstral-small-2 \
  --base-url http://GPU:1234/v1 "задача"

# облако, когда нужно качество
export OPENAI_API_KEY=sk-...
python3 -m agent -p openrouter -m anthropic/claude-sonnet-4 "задача"
```

### Три способа работы

```bash
python3 -m agent "почини падающий тест"        # разовая задача
python3 -m agent                                # диалог
make serve                                      # веб + API на :8080
```

### Автономный прогон

```bash
python3 -m agent --auto -P cad_auto --hours 8 \
  "оптимизировать редуктор: минимум габарита при i=20"

python3 -m agent --auto --resume 3    # продолжить после обрыва
```

### Роли

| профиль | навыки | для чего |
|---|---|---|
| `coder` | files, shell | разработка и отладка |
| `cad` | + cad | конструкции в OpenSCAD |
| `cad_auto` | + memory, present | автономное конструирование |
| `autonomous` | files, shell, memory, present, mcp | универсальное исследование |
| `research` | files, memory, present, mcp | анализ и выжимки |
| `marketing` | files, memory, present, mcp | тексты и лендинги |

Свой профиль — JSON в `agent/profiles/`. Свой навык — модуль с
`build(ws) -> list[Tool]` и строка в `SKILLS`.

### Внешние сервисы

```json
"mcp": { "servers": {
  "search": { "command": "npx", "args": ["-y", "...brave"], "rate_limit": 20 },
  "fetch":  { "command": "uvx", "args": ["mcp-server-fetch"], "rate_limit": 0 }
}}
```

Ваши серверы из LM Studio подключаются как есть. Лимит частоты на
каждый. Недоступный сервер не ломает агента.

### Проверка перед запуском

```bash
python3 -m agent --check -c examples/config.mcp.json
```

Покажет модель, песочницу, навыки и состояние каждого MCP-сервера.

## Часть 3. Моё мнение

### Что получилось хорошо

**Проверяемость.** 187 тестов, и каждый критичный проверен диверсией —
я ломал код и убеждался, что тест это ловит. Дважды тест оказывался
слепым, и я его усиливал. Это не формальность: именно так был найден
дефект с подстановкой цели.

**Автономность.** Память, онтология, перепланирование, детектор
зацикливания, возобновление после обрыва. Для суточной работы этого
достаточно.

**Лаконичность.** 3552 строки, ноль зависимостей, 24 МБ RSS. Всё
читается за вечер, чинится без археологии.

### Что мне не нравится

**Не проверено на живой модели.** У меня не было ключа. Вся логика
проверена на заглушках и настоящих сокетах, но как поведёт себя реальная
модель в восьмичасовом прогоне — я не знаю. Первый запуск делайте на
неважной папке с `-v`.

**Рефлексия дорогая.** Лишний вызов модели на каждой итерации, +15-20 %
токенов. Окупается, но на слабой модели может давать мусор.

**Планировщик наивный.** Разбивает задачу один раз, качество плана —
целиком на совести модели. Перепланирование чинит худший случай, но не
делает план умным.

**~~Нет повтора при сбое сети.~~** Сделано: три попытки с растущей
паузой, только для временных ошибок. Плюс учёт токенов и стоимости.

### Найденный по ходу дефект

Замеряя пределы SQLite, я обнаружил, что `recall()` работал в **130 раз
медленнее**, чем должен: `ORDER BY rank` ранжировал все совпадения, а не
только нужную десятку.

| фактов | было | стало |
|---|---|---|
| 10 000 | 3.1 мс | 0.18 мс |
| 100 000 | 37 мс | 0.24 мс |
| 300 000 | — | 0.31 мс |

Исправлено, добавлен тест на скорость с проверкой диверсией. Без замера
я бы этого не увидел — и в ответе про pgvector сослался бы на «медленный
SQLite», что было бы неправдой.

## Часть 4. PostgreSQL + pgvector — стоит ли?

### Короткий ответ

**Сейчас — нет. Потом — только pgvector, и не вместо SQLite, а рядом.**

### Что показали замеры

SQLite после исправления:

```
300 000 фактов | поиск 0.31 мс | база ~120 МБ
```

Для суточного прогона это с запасом. Агент за 8 часов накапливает
сотни, максимум тысячи фактов — не сотни тысяч. **Производительность
не является причиной переходить на PostgreSQL.**

### Где SQLite действительно проигрывает

Полнотекстовый поиск ищет по словам, а не по смыслу. Замер:

```
факт в базе:  "венец проваливался внутрь корпуса без опорного буртика"

запрос "буртик"            → найдено ✓
запрос "осевая фиксация"   → НИЧЕГО ✗
запрос "просадка детали"   → НИЧЕГО ✗
```

Вот это — настоящая проблема. Агент через 6 часов спросит «была ли
проблема с фиксацией», не вспомнит формулировку, ничего не найдёт и
начнёт исследовать заново.

### Честное сравнение

| критерий | SQLite + FTS5 | PostgreSQL + pgvector |
|---|---|---|
| зависимости | **ноль** | сервер БД + драйвер + модель эмбеддингов |
| развёртывание | файл | установка, настройка, бэкапы |
| память на 1 ГБ | 24 МБ | PG сам съест 100-200 МБ |
| поиск по словам | **0.3 мс на 300k** | сравнимо |
| **поиск по смыслу** | **не умеет** ✗ | **умеет** ✓ |
| несколько агентов параллельно | блокировки при записи | **честная конкурентность** ✓ |
| работа по сети | нет | **есть** ✓ |
| стоимость эмбеддингов | — | вызов модели на каждый факт |

### Когда переходить — проверено замерами

Два условия из трёх, которые я назвал в первой редакции, **не выдержали
проверки**. Перемерил и исправляю себя.

**Условие «несколько агентов» — оказалось неверным.** Я утверждал, что
SQLite сериализует запись и три агента — уже повод для PostgreSQL.
Замер:

```
3 потока  x300 записей: 0.1 с | ошибок 0
8 потоков x300 записей: 0.1 с | ошибок 0
4 процесса x400 записей: 0.3 с | ошибок 0
10 процессов x400 записей: 0.6 с | ошибок 0
```

Ни одной ошибки блокировки. WAL справляется с десятком параллельных
писателей на одной машине. **Это не повод переходить.**

**Условие «работа по сети» — остаётся верным.** SQLite по сети не
работает, тут вариантов нет.

**Условие «память на годы» — остаётся, но не из-за объёма.** Объём
SQLite тянет (0.31 мс на 300k). Причина — семантический поиск.

Итого реальных условий **два**: агенты на разных машинах, либо нужен
поиск по смыслу на больших объёмах.

### Векторы в SQLite — тоже перемерил

В первой редакции я написал «полный перебор ≈20 мс на тысячах фактов».
**Это было неверно.** Замер на чистом Python (размерность 384):

| фактов | память | поиск | вердикт |
|---|---|---|---|
| 1 000 | 1.5 МБ | **41 мс** | приемлемо |
| 5 000 | 7.3 МБ | **139 мс** | приемлемо |
| 20 000 | 29 МБ | **551 мс** | медленно |

А попытка держать векторы обычными списками Python на 50k **убила
процесс по памяти** — пришлось перейти на `array('f')`.

Вывод точнее прежнего: полный перебор на чистом stdlib работает
до **~5 000 фактов**. Это покрывает один-два проекта, но не годовую
память.

Если нужен объём больше — варианты по возрастанию цены:

1. `numpy` (одна зависимость) — тот же перебор ускоряется в десятки раз;
2. `sqlite-vec` — расширение SQLite для векторов, без сервера;
3. PostgreSQL + pgvector — когда уже есть сеть и несколько машин.

### Итог

| вопрос | ответ |
|---|---|
| PostgreSQL сейчас? | **нет** — 0.31 мс на 300k фактов, узкого места нет |
| pgvector сейчас? | **нет** — но семантический поиск нужен, начните с векторов в SQLite |
| Когда PostgreSQL? | **агенты на разных машинах** или семантический поиск на десятках тысяч фактов. «Несколько агентов на одной машине» — НЕ повод: 10 процессов пишут без ошибок |
| Что делать сегодня? | ~~повтор, учёт токенов, гибридный поиск~~ — сделано. Дальше: только при реальной нужде |

Главный довод: **я замерил, а не предположил** — и замеры дважды
опровергли мои же первоначальные утверждения:

- «SQLite сериализует запись, три агента — повод для PG» → **неверно**,
  10 процессов пишут без единой ошибки;
- «полный перебор векторов ≈20 мс» → **неверно**, 41 мс на 1k и 551 мс
  на 20k, а на списках Python процесс вообще падает по памяти.

Вердикт «PostgreSQL пока не нужен» от этого не изменился, но теперь он
опирается на числа, а не на моё впечатление. Если ваши условия
отличаются от замеренных — решение должно измениться.
