# AWOS — Agentic Workflow OS

**Среда для проектирования и запуска автономных AI-команд.** Позволяет
объединять агентов в цепочки создания ценности с автоматическим
контролем качества на каждом этапе.

Это описание **самой платформы**, а не агентов, которые на ней живут.
AWOS ничего не знает про маркетинг, юриспруденцию или разработку — она
знает про автономию, оркестрацию и результат. Специализация приходит
JSON-файлом; среда остаётся неизменной.

**Зависимостей нет** — только стандартная библиотека Python 3.10+.
`pip install` не нужен. 493 проверки проходят без сети и без ключей.

```bash
cd agentic_workflow_os
make test      # 493 проверки, ~6 секунд
make demo      # среда в работе на офлайн-модели, без ключей
make serve     # http://127.0.0.1:8070/dashboard
```

## Зачем нужна среда, если есть агенты

Один агент с инструментами решает задачу. Производственный цикл требует
большего: чтобы работу кто-то проверил, чтобы данные не потерялись между
исполнителями, чтобы человек мог вмешаться, и чтобы завтра можно было
объяснить, откуда взялась цифра в отчёте.

Наивная схема «ответ первого агента подставили в промпт второго»
разваливается на третьем шаге: контекст растёт квадратично, в него
попадают рассуждения и извинения модели, а на вопрос «почему в отчёте
эта цифра» ответить нечем.

AWOS даёт четыре механизма, одинаковых для любого агента.

### Role-Based Collaboration
Внутри **одного шага** работают три роли: **Исполнитель** делает,
**Критик** ищет дефекты, **Контролёр** решает — принять или вернуть.
Роли принадлежат среде, а не агенту: один и тот же профиль бывает
Исполнителем на одном шаге и Критиком на другом.

Критик отделён от Контролёра намеренно. Критику платят за найденные
дефекты, и он находит их всегда, включая косметические; дай ему право
решать — конвейер уйдёт в бесконечную шлифовку. Контролёр отвечает на
другой вопрос: *мешает ли дефект использовать результат?* — и вправе
принять работу с известными недостатками.

Возврат на доработку — это **новый ход с замечаниями в промпте**, а не
«попробуй ещё раз» тем же текстом: без явных замечаний модель выдаёт то
же самое другими словами.

### Context Synchronization
Общая **доска** (blackboard) на прогон. Данные лежат под именами
(`research_notes`, `brief`), а не «предыдущим сообщением»; шаг объявляет
в определении, что читает и что пишет. Запись **не затирает**
предыдущую — создаётся новая версия, поэтому «кто и когда изменил
значение» — обычный запрос к истории, а не расследование по логам.

В промпт уходит только то, что шаг объявил в `reads`. Это прямая
экономия токенов и защита от того, что модель зацепится за чужой
черновик.

### Human-in-the-Loop
Точка контроля — это **состояние в базе, а не ожидание в памяти**.
Среда создаёт запись, переводит прогон в `waiting_human` и выходит.
Человек отвечает позже — из CLI, из HTTP API, из консоли, хоть на
следующий день, — и любой процесс с той же базой продолжает прогон с
того же места.

Человек может утвердить, отклонить или **прислать исправленный текст**
— он и станет результатом шага. Это дешевле любой доработки моделью и
единственный способ гарантированно получить нужный результат, когда
модель раз за разом промахивается.

### Tool Integration
Инструменты — **системные вызовы среды**, а не способности агента.
Набор создаёт среда по своим грантам; профиль агента и шаг могут только
**сузить** его. Профиль, присланный со стороны, не в состоянии выписать
себе доступ к shell или к внутренней сети. Каждый вызов пишется в
журнал; опасные требуют подтверждения человека **до** выполнения.

## Быстрый старт

### Без ключей и без сети

```bash
make demo
```

Прогонит настоящий workflow на детерминированной офлайн-модели: два
шага, цикл качества, запись на доску. Так проверяют, что среда жива, и
отлаживают собственные определения, не тратя токены.

### С настоящей моделью

```bash
export AWOS_API_KEY=sk-...            # или AWOS_BASE_URL на LM Studio
python3 -m awos check                 # самопроверка окружения

python3 -m awos run research_brief \
  --goal "понять, стоит ли нам переходить на ClickHouse" \
  --input topic="ClickHouse против PostgreSQL для аналитики" \
  --input audience="технический директор"
```

Прогон остановится на утверждении брифа:

```
⏸ Прогон #1: waiting_human
  ✓ research score=0.86
  ⏸ brief score=0.91

⏸ Нужен человек — точка контроля #1 (approval)
  Утвердите результат шага (можно прислать правку).
  --- результат на утверждение ---
  ...

  awos approve 1            — утвердить
  awos edit 1 'текст'       — утвердить с правкой
  awos reject 1 'причина'   — отклонить
```

Ответить можно когда угодно и из любого процесса:

```bash
python3 -m awos inbox          # что ждёт решения
python3 -m awos approve 1      # прогон доигрывается сам
```

### Локальная модель (LM Studio / Ollama / llama.cpp / vLLM)

```bash
export AWOS_BASE_URL=http://localhost:1234/v1
export AWOS_MODEL=qwen2.5-14b-instruct
export AWOS_API_KEY=                  # обычно не нужен
```

Среда не использует нативный tool-calling: вызовы инструментов идут
текстовым протоколом (см. ниже), поэтому локальные сборки работают так
же, как облако.

## Определение workflow

Последовательность шагов задаёт **человек**, а не модель. Ни один
прогон не решает, какой шаг будет следующим, кто его выполнит и какие
инструменты ему доступны — модель решает только содержание ответа
внутри шага. Это осознанное ограничение: производственный цикл должен
быть воспроизводимым.

`awos/workflows/research_brief.json`:

```json
{
  "name": "research_brief",
  "title": "Исследование → бриф",
  "inputs": {"topic": "тема", "audience": "для кого"},
  "steps": [
    {
      "name": "research",
      "profile": "researcher",
      "task": "Собери материал по теме: {input.topic}",
      "writes": "research_notes",
      "review": {"critic": "fact_checker", "min_score": 0.7, "max_revisions": 2}
    },
    {
      "name": "brief",
      "profile": "writer",
      "task": "Сведи материал в бриф для: {input.audience}",
      "reads": ["research_notes"],
      "writes": "brief",
      "review": {"critic": "critic", "supervisor": "supervisor"},
      "human": "always"
    }
  ]
}
```

**Плейсхолдеры:** `{goal}` — цель прогона, `{input.x}` — вход,
`{ctx.key}` — значение с доски, `{step.name}` — результат шага.

**`human`:** `never` | `always` | `on_reject` | `default` (политика среды).

**Валидация до запуска.** Опечатка `{input.topik}`, ссылка на ключ,
который никто не пишет, дубль имени шага, `reads` на несуществующее —
всё это ошибка **до первого обращения к модели**, с указанием, что
именно не так и что доступно вместо этого. Обнаружить такое через
десять минут прогона и двести тысяч токенов — недопустимо.

## Профиль агента

Специализация — это данные, а не код: `awos/profiles/researcher.json`.

```json
{
  "name": "researcher",
  "role": "worker",
  "system": "Ты — Исполнитель в роли аналитика...",
  "tools": ["read_file", "http_request", "sql_query"],
  "temperature": 0.2
}
```

Профиль может: задать промпт, выбрать модель, **сузить** инструменты.
Профиль **не может**: расширить набор инструментов сверх грантов среды,
включить shell, изменить политику HITL, поднять лимит доработок. Это
решения администратора среды.

В поставке: `researcher`, `writer`, `engineer` (worker), `critic`,
`fact_checker` (critic), `supervisor`. Среда работает и без единого
файла — есть встроенные роли по умолчанию.

## Инструменты и гранты

| Инструмент | Грант среды | Примечание |
|---|---|---|
| `read_file`, `write_file`, `list_files` | всегда | строго внутри рабочей папки |
| `current_time` | всегда | |
| `http_request` | `AWOS_HTTP_ALLOW` | **белый** список хостов |
| `sql_query` | `AWOS_SQL_DATABASES` | только SELECT/WITH, соединение `mode=ro` |
| `shell` | `AWOS_ALLOW_SHELL` | опасный: подтверждение человека до вызова |
| `context_read`, `context_write` | всегда | побочные записи на доску |

Белый список, а не чёрный: среда исполняет текст, сгенерированный
моделью, и «запретить лишнее» здесь принципиально ненадёжно.

**Протокол вызова** — строгий JSON в тексте ответа:

````
```tool
{"tool": "read_file", "args": {"path": "notes.md"}}
```
````

Нативный tool-calling не используется намеренно: поддержка `tools` у
локальных сборок неровная, а текстовый протокол работает везде одинаково
и делает вызов видимым — он лежит в журнале как есть и воспроизводится
при разборе инцидента. Разбор снисходителен к оформлению (метка ```json,
голый JSON, текст вокруг) и строг к содержанию (неизвестный инструмент,
`args` не-объект, два вызова за ход — отказ с объяснением модели).

**Ошибка инструмента не роняет прогон**: текст уходит модели, и она
обычно исправляется сама.

## HTTP API и веб-консоль

```bash
make serve      # http://127.0.0.1:8070/dashboard
```

Консоль — один HTML-файл на ванильном JS, без сборки и зависимостей:
прогоны с журналом и доской, запуск, очередь согласований с кнопками
«Утвердить / с правкой / Отклонить», каталог workflow, профилей и грантов.

```
GET  /health                        без токена
GET  /, /dashboard                  консоль
GET  /v1/workflows | /v1/profiles | /v1/tools | /v1/config | /v1/stats
POST /v1/runs                       {workflow, goal, inputs}
GET  /v1/runs | /v1/runs/<id>
GET  /v1/runs/<id>/events?after=N   журнал для «живого» обновления
GET  /v1/runs/<id>/context[?key=]   доска: срез или история ключа
POST /v1/runs/<id>/resume | /cancel
GET  /v1/checkpoints[?run_id=]      очередь согласований
POST /v1/checkpoints/<id>           {status: approved|rejected|edited|cancelled,
                                     response}
```

Если задан `AWOS_API_TOKEN` — все маршруты, кроме `/health` и статики,
требуют `Authorization: Bearer <token>`. **Слушать не-localhost без
токена среда отказывается**: здесь исполняется текст модели и
вызываются инструменты, открытый порт означает отданную машину.

## Устройство

```
awos/
  config.py          Config: умолчания -> JSON -> окружение; секреты только
                     из окружения, гранты инструментов, валидация
  contracts.py       маркеры ролей — нижний слой без зависимостей
  kernel/
    store.py         SQLite: run/step/context/checkpoint/event/tool_call
    workflow.py      разбор и ПОЛНАЯ валидация определения до запуска
    engine.py        ЯДРО: порядок шагов, цикл качества, HITL, аудит
  roles/

    worker.py        ход Исполнителя: модель -> инструменты -> модель

  tools/
    base.py          Tool, ToolRegistry, Workspace (изоляция путей)
    protocol.py      текстовый протокол вызова
    builtin.py       файлы, HTTP, SQL, shell, доска, время
    registry.py      сборка набора из грантов среды
  llm/
    base.py          контракт chat(messages) -> Reply + retry
    openai_like.py   любой OpenAI-совместимый /v1
    stub.py          детерминированный офлайн-провайдер
  api/
    server.py        HTTP API на стандартной библиотеке
    web/console.html веб-консоль одним файлом
  workflows/         research_brief, code_review, document_pipeline
  profiles/          researcher, writer, engineer, critic, fact_checker,
                     supervisor
tests/               493 проверки: реальный SQLite, реальные сокеты,
                     реальные подпроцессы; заглушка только на месте модели
```

### Почему SQLite

Состояние обязано пережить перезапуск процесса — иначе пауза на
человеке превращается в «подождите, не закрывайте вкладку». SQLite даёт
это одним файлом, без внешнего сервера и без зависимостей. Там, где
нужен векторный поиск по онтологии, стоит соседний проект MAOS с
PostgreSQL+pgvector; здесь семантики нет вообще — только строго
типизированное состояние процесса.

### Что среда не делает

Не планирует, не декомпозирует цель и не выбирает исполнителя «по
смыслу». Нет «агента, который руководит агентами». Для семантического
выбора агента есть соседний `multi_agent_system_ontology`. Здесь план
приходит от человека в виде JSON — ради воспроизводимости.

## Тесты

```bash
make test    # 493 проверки, ~6 секунд, без сети и без ключей
```

Философия — как у соседей по репозиторию: никаких фреймворков, скрипт
на стандартной библиотеке, **реальная инфраструктура** (настоящий
SQLite, настоящие сокеты `ThreadingHTTPServer`, настоящие подпроцессы
для CLI), заглушка ровно одна — на месте самой модели.

| Набор | Проверок | О чём |
|---|---|---|
| `test_config.py` | 38 | приоритеты, секреты не читаются из файла, валидация |
| `test_store.py` | 55 | версии доски, точки контроля, переживание перезапуска |
| `test_workflow.py` | 49 | валидация до запуска, ошибки в плейсхолдерах |
| `test_tools.py` | 72 | изоляция путей, белый список, SELECT-only, протокол |
| `test_roles.py` | 82 | сломанный JSON критика, сбои модели, лимиты, retry |
| `test_engine.py` | 85 | цикл качества, доска, HITL через «перезапуск процесса» |
| `test_api.py` | 57 | токен, полный HITL по HTTP, коды ошибок |
| `test_cli.py` | 55 | сквозной сценарий разными процессами |

Негативных сценариев больше, чем позитивных, и это намеренно: ценность
платформы в том, как она ведёт себя с **плохими** ответами модели —
сломанным JSON, пустым текстом, бесконечными вызовами инструментов,
отказом провайдера, попыткой выйти за пределы рабочей папки.

Что проверяется отдельно, потому что стоит дороже всего:

* **брак не принимается молча** — исчерпание доработок ведёт к провалу
  шага или к эскалации человеку, но никогда к тихой приёмке;
* **пауза переживает процесс** — новый `Engine` на той же базе видит
  открытую точку контроля и доигрывает прогон;
* **прогон исполняет ту редакцию workflow, с которой стартовал** — правка
  файла не ломает идущие прогоны;
* **подтверждение опасного вызова происходит ДО выполнения** — журнал
  вызовов пуст, пока человек не ответил;
* **сужение прав необратимо** — шаг не может вернуть инструмент,
  отобранный профилем.

## Соседи по репозиторию

Три независимых проекта с общей философией и **без общего кода**:

| Проект | Про что |
|---|---|
| `agent_system` | один автономный агент с инструментами |
| `multi_agent_system_ontology` | агенты-личности, семантический роутер, онтология в PostgreSQL+pgvector |
| **`agentic_workflow_os`** | **сама среда: детерминированное ядро, цикл качества, HITL, аудит** |

AWOS не импортирует соседей в рантайме и версионируется отдельно.
