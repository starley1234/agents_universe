# ERP AI («АСУП ИИ») — ядро + сквозной сценарий агента-снабженца

Реализация ключевой части ТЗ на AI-ориентированную ERP-систему для
малых производств: ядро документооборота снабжения на PostgreSQL,
интеграционный адаптер к 1С по EnterpriseData-подобному протоколу, и
**один полностью работающий сквозной AI-сценарий — агент-снабженец**,
демонстрирующий ВСЮ обязательную агентскую архитектуру из ТЗ
(explainability, confirmation gates, guardrails, audit trail, rollback,
настраиваемые режимы автономности).

Независимое приложение, живущее рядом с `agent_system/` и
`multi_agent_system_ontology/` в этом репозитории — не зависит от них
в рантайме. Общий стиль (докстрины "почему", тесты на реальной
инфраструктуре, секреты только в окружении) позаимствован осознанно.

## Честная граница объёма — что реализовано, а что нет

Полное ТЗ описывает продукт на 21 месяц разработки (production/
snabжение/склад/финансы/HR контуры, AI-Onboarding, мультитенант SaaS,
React+TS фронтенд, Kafka/ClickHouse/Kubernetes, LangGraph-оркестрация
множества доменных агентов, мобильные приложения). Ни один инструмент
не может добросовестно "реализовать" это за одну сессию — вместо
имитации широты через заглушки выбран противоположный подход:
**реализовать один контур и одного агента полностью и по-настоящему**,
на реальной инфраструктуре, с честными тестами.

### Реализовано (по-настоящему, с тестами на реальной инфраструктуре)

- **Ядро документооборота снабжения**: справочники номенклатуры и
  контрагентов, цены поставщиков, остатки по складам с резервом, заявки
  на закупку, заказы поставщикам со строками (`app/db/store.py`).
- **Агент-снабженец** (`app/agents/procurement.py`) — ТЗ §3.4/§3.7:
  - анализ дефицита (доступный остаток < страхового запаса);
  - выбор поставщика по минимальной цене СРЕДИ ДОСТАТОЧНО НАДЁЖНЫХ
    (не просто самый дешёвый — компромисс явно объясняется);
  - **Explainability** — текстовое обоснование + структурированные
    `sources` (на основании каких именно данных принято решение);
  - **Confirmation gates** — 4 настраиваемых режима автономности
    (`suggest`/`draft`/`auto_with_review`/`full_auto`);
  - **Guardrails** — сумма выше `PROCUREMENT_MAX_AUTO_AMOUNT` НИКОГДА
    не проводится автоматически, даже при `full_auto` — проверяется в
    коде агента, а не только в конфигурации/UI;
  - **Audit trail** — каждое решение (агента и человека) пишется в
    неизменяемый журнал (`audit_log`, только `INSERT` в коде `Store`);
  - **Rollback** — отмена `full_auto`-решения возможна, пока заказ не
    отправлен в 1С (после отправки — сознательное ограничение, во
    избежание рассинхронизации).
- **Интеграция с 1С** (`app/integrations/onec_adapter.py`) — РЕАЛЬНЫЙ
  HTTP+XML обмен по протоколу, структурно повторяющему EnterpriseData
  (`<Файл>/<Документ>/<Контрагент>/<Товары>`): выгрузка заказа
  поставщику, загрузка справочников номенклатуры/контрагентов,
  идемпотентность (повторный вызов не отправляет документ дважды),
  журнал попыток и ошибок, настраиваемая мастер-система для каждого
  справочника (`erp` или `1c` побеждают при конфликте).
- **HTTP API** на FastAPI (`app/api/server.py`) — REST, токен-защита.
- **Веб-дашборд** (`app/web/dashboard.html`) — обзор, дефицит и запуск
  скана агентом, предложения с кнопками утвердить/отклонить/откатить,
  заказы поставщикам с отправкой в 1С, журнал аудита.

### НЕ реализовано (осознанно, не притворяемся, что готово)

- Производственный, складской (кроме остатков), финансовый, кадровый
  контуры — только справочники/остатки в объёме, нужном снабжению.
- AI-Onboarding (диалоговая настройка системы) — отдельный крупный
  модуль ТЗ §3.1, требует отдельного проектирования.
- Доменные агенты кроме снабженца (планировщик, кладовщик, продажник,
  финансист, аналитик) — архитектура агента переиспользуема (см.
  `app/agents/procurement.py` как образец), но сами агенты не написаны.
- Реальный сервер 1С — адаптер протестирован на локальном fake-HTTP-
  сервере, эмулирующем протокол; интеграция с настоящей конфигурацией
  1С:Предприятия потребует дополнительной проверки на реальном стенде.
- GraphQL API, вебхуки, ЭДО, маркировка, банковские выписки, MQTT/IoT.
- React+TypeScript фронтенд — дашборд на vanilla JS, как в остальных
  проектах этого репозитория (без сборки, без Node.js в рантайме).
- LangGraph/LangChain-оркестрация — один агент реализован напрямую, без
  фреймворка оркестрации (для одного агента он не нужен архитектурно).
- Kafka/ClickHouse/Kubernetes/Redis/MinIO — не нужны для объёма,
  который реально реализован; добавлены бы карго-культом.
- Мультитенантность, RBAC/ABAC, шифрование at-rest, 152-ФЗ-аудит.

## Требования

- Python 3.10+
- PostgreSQL 14+ (без `pgvector` — не нужен для этого контура)
- `pip install -r requirements.txt` (FastAPI/uvicorn/psycopg)
- Для тестов: `pip install -r requirements-dev.txt` (`pgserver` —
  embedded PostgreSQL, `httpx` — HTTP-клиент для тестов API)

## Быстрый старт

```bash
cd erp_ai
pip install -r requirements.txt

cp .env.example .env
# отредактируйте DB_DSN — реальный PostgreSQL, например:
# DB_DSN=postgresql://erp:erp@localhost:5432/erp_ai

export $(grep -v '^#' .env | xargs)
make serve      # http://127.0.0.1:8100/dashboard
```

Для тестов (нужен `pgserver`, БД поднимается автоматически во время
тестового прогона, реальная PostgreSQL не требуется):

```bash
pip install -r requirements-dev.txt
make test       # 182 проверки, ~15 секунд
```

## Сценарий агента-снабженца — пошагово

```bash
# 1. Завести номенклатуру со страховым запасом
curl -X POST localhost:8100/v1/nomenclature \
  -d '{"sku":"MTL-001","name":"Сталь листовая 2мм","unit":"лист","min_stock":100}'

# 2. Завести поставщика и цену
curl -X POST localhost:8100/v1/counterparties \
  -d '{"name":"ЗАО СтальТорг","reliability_score":0.9}'
curl -X POST localhost:8100/v1/counterparties/1/prices \
  -d '{"nomenclature_id":1,"price":1400.0}'

# 3. Установить текущий остаток (ниже страхового запаса -> дефицит)
curl -X POST localhost:8100/v1/nomenclature/stock \
  -d '{"nomenclature_id":1,"quantity":10}'

# 4. Запустить скан дефицита агентом-снабженцем
curl -X POST localhost:8100/v1/agents/procurement/scan \
  -d '{"autonomy_mode":"draft"}'
# -> предложение с explainability: почему, какой поставщик, сколько

# 5. Человек утверждает предложение (confirmation gate)
curl -X POST localhost:8100/v1/proposals/1/approve -d '{"actor":"human:ivanov"}'
# -> создан реальный заказ поставщику

# 6. Отправить заказ в 1С (адаптер, идемпотентно)
curl -X POST localhost:8100/v1/purchase-orders/1/sync-1c
```

Смена `autonomy_mode` на `full_auto` при небольшой сумме заказа
приведёт к тому, что шаг 5 не понадобится — заказ будет создан
автоматически (`status: auto_executed`), но останется в аудите и
доступен для `rollback`, пока не отправлен в 1С.

## HTTP API

```
GET  /health                          — жив ли сервис (без токена)
GET  /dashboard, /                    — веб-интерфейс

GET  /v1/nomenclature                 — справочник номенклатуры
POST /v1/nomenclature                 — создать/обновить позицию
GET  /v1/nomenclature/low-stock       — позиции с дефицитом
POST /v1/nomenclature/stock           — установить остаток

GET  /v1/counterparties               — справочник контрагентов
POST /v1/counterparties               — создать/обновить контрагента
POST /v1/counterparties/{id}/prices   — задать цену поставщика

GET  /v1/purchase-orders              — список заказов поставщикам
GET  /v1/purchase-orders/{id}         — детали заказа
POST /v1/purchase-orders/{id}/sync-1c — выгрузить в 1С

POST /v1/agents/procurement/scan               — скан дефицита, пачка предложений
POST /v1/agents/procurement/propose/{nom_id}   — предложение по одной позиции
GET  /v1/proposals                    — список предложений агента
GET  /v1/proposals/{id}               — детали + explainability + audit_trail
POST /v1/proposals/{id}/approve       — confirmation gate: утвердить
POST /v1/proposals/{id}/reject        — confirmation gate: отклонить
POST /v1/proposals/{id}/rollback      — откат full_auto решения

GET  /v1/audit                        — журнал аудита (неизменяемый)
GET  /v1/audit/{entity_type}/{id}     — аудит по конкретному документу
POST /v1/onec/pull/nomenclature       — 1С -> ERP: загрузить номенклатуру
POST /v1/onec/pull/counterparties     — 1С -> ERP: загрузить контрагентов
GET  /v1/onec/sync-log                — журнал обмена с 1С

GET  /v1/dashboard/stats              — статистика для обзора
```

Токен: если задан `ERP_API_TOKEN`, все маршруты кроме `/health` и
`/dashboard` требуют `Authorization: Bearer <token>`. Сервер
отказывается слушать не-localhost без токена.

## Структура проекта

```
app/
  config.py              — Config: DB_DSN обязателен, guardrails, 1С
  db/store.py             — PostgreSQL: справочники, документы снабжения,
                            agent_proposal, audit_log (неизменяемый),
                            onec_sync_log (идемпотентность обмена)
  agents/procurement.py   — сквозной сценарий: ProcurementAgent
                            (вся обязательная агентская архитектура ТЗ)
  integrations/
    onec_adapter.py        — HTTP+XML обмен с 1С (EnterpriseData-подобный)
  api/server.py           — HTTP API на FastAPI
  server.py               — точка входа: python3 -m app.server
  web/dashboard.html      — веб-интерфейс на vanilla JS
tests/                    — 182 проверки, реальный embedded PostgreSQL
                            (pgserver), реальный uvicorn-сервер, реальный
                            fake-HTTP-сервер, эмулирующий 1С — без моков
```

## Тесты

```bash
make test   # 182 проверки, ~15 секунд
```

Философия — как в остальных проектах этого репозитория: реальная
инфраструктура (embedded Postgres, реальные HTTP-серверы), обязательные
негативные сценарии (guardrail нельзя обойти, повторный approve
отклоняется, rollback после синхронизации с 1С запрещён), отсутствующие
опциональные зависимости приводят к graceful skip, а не к падению
всего набора.
