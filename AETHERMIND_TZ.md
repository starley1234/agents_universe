# AetherMind: Autonomous Iterative Engine — техническое задание

Дата подготовки: 2026-08-04  
Статус: draft / development  
Проект: `AetherMind`

## 1. Краткое описание

**AetherMind** — платформа для запуска долгоживущих автономных ИИ-агентов, которые выполняют сложные исследовательские и инженерные задачи в течение часов через циклы планирования, исполнения, наблюдения, рефлексии и самокоррекции.

Цель системы — превратить LLM из чат-бота в автономного цифрового сотрудника: пользователь формулирует цель, а система самостоятельно планирует работу, выполняет операции, сохраняет прогресс, контролирует бюджет и предоставляет прозрачный мониторинг процесса.

## 2. Основная продуктовая идея

AetherMind работает не как линейный чат, а как **Mission Control** для автономных агентов:

- агент получает долгосрочную цель;
- дробит ее на подзадачи;
- выполняет действия инструментами;
- сохраняет состояние после каждого шага;
- оценивает уверенность и качество результата;
- при необходимости откатывается, меняет план или запрашивает человека;
- формирует материальные артефакты: отчеты, таблицы, код, PDF, JSON, CSV и другие файлы.

## 5. Архитектура агентного цикла

### 5.1. Базовая модель цикла

Агент работает по состоянию, а не по разовому запросу.

```text
Plan -> Execute -> Observe -> Reflect -> Persist -> Route
```

### 5.2. Узлы графа

1. **Plan**  
   Декомпозиция цели, построение подзадач, выбор стратегии и инструментов.

2. **Execute**  
   Выполнение действия: поиск, чтение файлов, запуск кода, работа с браузером, генерация артефактов.

3. **Observe**  
   Сбор результатов действия, ошибок, логов, файлов и внешних данных.

4. **Reflect**  
   Оценка результата, выявление ошибок, принятие решения о продолжении, откате, паузе или завершении.

5. **Summarize**  
   Периодическое сжатие контекста в executive summary.

6. **Persist**  
   Сохранение состояния, снапшота, событий, бюджета и артефактов.

7. **Human Gate**  
   Переход в `AWAITING_USER`, если требуется подтверждение или выбор стратегии.

### 5.3. Статусы задачи

- `PENDING` — задача создана, но не запущена.
- `RUNNING` — агент выполняет итерации.
- `PAUSED` — пользователь поставил задачу на паузу.
- `AWAITING_USER` — требуется ввод или подтверждение человека.
- `SLEEPING` — задача временно остановлена из-за лимитов или расписания.
- `FAILED` — задача завершилась ошибкой.
- `COMPLETED` — цель достигнута, финальный результат готов.
- `ROLLED_BACK` — выполнен откат к предыдущему состоянию.

## 6. Управление контекстом и памятью

### 6.1. Recursive Summarization

Каждые 5–10 итераций система запускает скрытую саммаризацию истории:

- что было сделано;
- что не сработало;
- какие данные найдены;
- какие решения приняты;
- какие риски остались;
- какой следующий шаг рекомендован.

Цель — подавать в LLM не гигантский лог, а компактный executive summary + актуальное состояние.

### 6.2. Scratchpad Memory

Для каждой задачи ведется обновляемый рабочий буфер:

- промежуточные факты;
- гипотезы;
- ссылки на источники;
- список уже проверенных направлений;
- ошибки и решения;
- краткая карта текущей стратегии.

### 6.3. Long-term Memory

В Postgres + pgvector хранятся:

- эмбеддинги документов;
- важные наблюдения;
- завершенные выводы;
- reusable patterns;
- пользовательские предпочтения, если это разрешено настройками приватности.

## 7. Персистентность и отказоустойчивость

### 7.1. State Snapshots

После каждого шага агент сохраняет JSON-состояние:

- текущая цель;
- текущий план;
- номер итерации;
- последние действия;
- observation;
- confidence;
- бюджет;
- ссылки на созданные файлы;
- контекстные summaries;
- статус задачи.

### 7.2. Восстановление после сбоя

При падении сервера или воркера:

1. Celery-задача восстанавливается из очереди или переинициализируется.
2. Последний валидный снапшот читается из Postgres.
3. Агент продолжает работу с последней устойчивой точки.

### 7.3. Time-Travel Debugging

Пользователь может:

- выбрать предыдущий чекпоинт;
- посмотреть состояние агента на тот момент;
- изменить вводные;
- запустить новую ветку выполнения.

- извлечение структурированных данных;

Все выполнение должно происходить в Docker sandbox с лимитами CPU, RAM, времени и файлового доступа.

### 8.3. File System

Для каждой задачи создается выделенный workspace:

```text

  tasks/
    {task_id}/

      code/
```

Агенту доступны контролируемые инструменты:

- `list_dir`;
- `read_file`;
- `write_file`;
- `append_file`;
- `delete_file` только через guardrail;
- `export_artifact`.

### 8.4. MCP Integrations

Система должна поддерживать подключение внешних MCP-серверов:

- поиск;
- кастомный агентный toolkit;
- корпоративные источники данных;
- внутренние инструменты.

## 9. Human-in-the-loop и контроль

### 9.1. Confidence Scoring

После каждого шага агент возвращает оценку уверенности:

```json
{
  "confidence": 0.82,
  "reason": "Источник подтвержден двумя независимыми страницами, данные согласованы."
}
```

Если уверенность ниже порога несколько раз подряд, система должна:

- усилить prompt;
- переключить модель на более сильную;
- запросить человека;
- предложить rollback;
- остановить дальнейшие рискованные действия.

### 9.2. Budget Guardrails

Контролируются:

- лимит токенов;
- лимит стоимости;
- лимит времени;
- лимит числа инструментальных вызовов;
- лимит браузерных действий;
- лимит Docker-выполнений.

При достижении лимита агент переходит в `SLEEPING` или `AWAITING_USER` с сохранением прогресса.

### 9.3. Safety Confirmation

Опасные действия требуют подтверждения пользователя:

- удаление файлов;
- отправка форм;
- платежи;
- внешние публикации;
- действия с production-инфраструктурой;
- сетевое сканирование вне явно разрешенной области.

## 10. Интерфейс Mission Control

### 10.1. Strategy Graph

Интерактивная карта задач и подзадач:

- зеленый — завершено;
- синий — выполняется;
- красный — ошибка или пересмотр;
- серый — ожидает запуска;
- янтарный — требует внимания.

По клику на узел отображаются:

- входные данные;
- действие агента;
- observation;
- reasoning summary без раскрытия приватных chain-of-thought;
- уверенность;
- связанные артефакты.

### 10.2. Live Trace & Thought Log

Поток событий:

- `Thought Summary` — краткое объяснение решения;
- `Action` — вызванный инструмент;
- `Observation` — результат;
- `Reflection` — оценка;
- `Error` — ошибка;
- `Checkpoint` — сохраненное состояние.

Должен быть фильтр «Без воды», скрывающий низкоуровневый технический шум.

### 10.3. Artifacts Canvas

Правая зона интерфейса:

- live document;
- file explorer;
- встроенный редактор;
- просмотр CSV/таблиц;
- просмотр изображений и PDF;
- code sandbox preview.

### 10.4. Control & Guardrails Panel

Панель управления:

- token meter;
- cost meter;
- confidence gauge;
- context heatmap;
- checkpoint slider;
- кнопка `Pause`;
- кнопка `Intervene`;
- кнопка `Rollback`;
- кнопка `Resume`;
- статус задачи.

### 10.5. Snapshot View

Если пользователь возвращается после перерыва, интерфейс показывает дайджест:

- сколько шагов выполнено;
- какие ошибки произошли;
- какие артефакты созданы;
- текущая подзадача;
- требуется ли действие пользователя.

## 11. Масштабируемость

### 11.1. Horizontal Scaling

Благодаря Celery и Redis система должна поддерживать горизонтальное масштабирование воркеров:

- 1 агент = 1 активная long-running task или набор коротких итераций;
- можно добавлять воркеры на разных серверах;
- очередь распределяет задачи;
- состояние не хранится в памяти воркера, а фиксируется в БД.

### 11.2. Model Routing

Система автоматически выбирает модель по сложности шага:

- сложное планирование — сильная модель;
- рутинное извлечение — дешевая модель;
- критика результата — сильная модель;
- форматирование — дешевая модель;
- низкая уверенность — escalation на более сильную модель.

### 11.3. Stateless Workers

Воркеры должны быть максимально stateless:

- весь прогресс в Postgres;
- артефакты в workspace/object storage;
- события в event log;
- воркер можно остановить и заменить без потери состояния.

## 14. Нефункциональные требования

### 14.1. Безопасность

- секреты только в переменных окружения или secret manager;
- Docker sandbox с ограничениями;
- allowlist сетевых целей для чувствительных операций;
- audit log всех инструментальных вызовов;
- подтверждение человека для опасных действий;
- запрет автономных платежей и production-действий без human approval.

### 14.2. Наблюдаемость

- трассировка LLM-вызовов;
- event log по каждой итерации;
- метрики токенов, стоимости и времени;
- статус Celery workers;
- healthchecks API, Redis, Postgres и sandbox runtime.

### 14.3. Производительность

- UI должен получать обновления в реальном времени без polling-heavy архитектуры;
- долгая работа агента не должна блокировать FastAPI;
- воркеры должны масштабироваться горизонтально;
- большие артефакты не должны храниться в JSON-состоянии.

### 14.4. Надежность

- идемпотентность итераций там, где возможно;
- retry policy для временных ошибок;
- dead-letter queue для неразрешимых сбоев;
- checkpoint после каждого значимого шага;
- возможность возобновления после рестарта.

## 15. MVP Scope

### 15.1. Входит в MVP

- создание задачи через API;
- запуск агентного цикла через Celery;
- базовый LangGraph: `plan -> execute -> reflect -> persist`;
- сохранение задач, событий и снапшотов в Postgres;
- workspace на файловой системе;
- basic tools: read/write/list files, Python execution sandbox;
- простая recursive summarization каждые N итераций;
- confidence scoring;
- budget limits;
- frontend dashboard с trace, статусом, файлами и управлением pause/resume;
- `.env.example` и docker-compose для локальной разработки.

### 15.2. Не входит в MVP / позже

- полноценный интерактивный graph editor;
- сложный browser automation с антибот-обходом;
- multi-agent collaboration;
- object storage для артефактов;
- advanced time-travel branching UI;
- marketplace MCP-инструментов;
- enterprise RBAC и SSO.

## 16. Риски и ограничения

| Риск | Вероятность | Влияние | Митигация |
|---|---:|---:|---|
| Агент уходит в бесконечный цикл | Высокая | Высокое | budget guardrails, max iterations, reflection, confidence threshold |
| Рост стоимости LLM | Высокая | Высокое | model routing, summarization, caching |
| Потеря состояния при сбое | Средняя | Высокое | snapshots after every step, stateless workers |
| Небезопасное выполнение кода | Средняя | Критическое | Docker sandbox, seccomp, resource limits, no privileged mode |
| Низкое качество источников | Средняя | Среднее | source scoring, cross-checking, reflection |
| UI перегружен логами | Средняя | Среднее | фильтр «Без воды», summaries, уровни детализации |
| Секреты попали в репозиторий | Низкая | Критическое | `.env.example`, secret scanning, pre-commit hooks |

## 18. Acceptance Criteria для MVP

MVP считается готовым, если:

- [ ] пользователь может создать задачу через API/UI;
- [ ] задача запускается в Celery worker;
- [ ] агент выполняет минимум 3 итерации `plan -> execute -> reflect`;
- [ ] после каждой итерации создается snapshot в Postgres;
- [ ] после рестарта worker задача продолжается с последнего snapshot;
- [ ] UI показывает live trace и текущий статус;
- [ ] агент создает хотя бы один артефакт в workspace;
- [ ] budget guardrail останавливает задачу при лимите;
- [ ] confidence ниже порога переводит задачу в безопасный режим или запрашивает человека;
- [ ] пользователь может поставить задачу на паузу и продолжить;
- [ ] реальные секреты не хранятся в репозитории.

## 20. Краткое резюме

AetherMind должна быть не «самым умным агентом», а **умной средой исполнения**, которая:

- сохраняет каждое важное состояние;
- ограничивает бюджет и риск;
- предоставляет агенту безопасные инструменты;
- сжимает контекст;
- позволяет человеку вмешиваться асинхронно;
- визуализирует ход работы прозрачно и управляемо.

Именно надежная среда, а не только промпт, делает многочасовую автономную работу агента практичной и масштабируемой.
