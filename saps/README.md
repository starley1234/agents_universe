# САПС — Система агентской поддержки сертификации

**САПС не заменяет Teamcenter, а является его интеллектуальным
фронтендом**, который берёт на себя грязную работу по подготовке данных,
гарантируя, что в основную систему попадут только валидные и готовые к
проверке регулятором требования.

Назначение: сбор, очистка и верификация требований лётной годности,
подготовка доказательной документации для конструкторских бюро.
Пользователи: инженеры-конструкторы и инженеры по сертификации.

```bash
cd saps
pip install -r requirements.txt
make demo      # весь путь на временной базе, без настройки
make test      # 638 проверок, ~16 секунд
```

**Развернуть у себя:** [QUICKSTART.md](QUICKSTART.md) — Docker за пять
минут или установка на хост через systemd, с бэкапами, мониторингом и
разбором типичных ошибок.

```bash
cp .env.example .env      # заполнить POSTGRES_PASSWORD и SAPS_API_TOKEN
docker compose up -d --build
docker compose run --rm saps migrate
```

## Одна команда на документ

```bash
saps load Авиационные_правила_25.pdf     # справочник АП
saps load ТЗ_на_изделие.docx             # требования
```

Система сама определит, что это за документ, разберёт его, положит в
базу, посчитает эмбеддинги и запустит агентов. Ничего не будет изменено
без вашего решения — агенты только готовят предложения.

```
Документ: Авиационные_правила_25.pdf
Тип: pdf, назначение: справочник авиационных правил

  ✓ Тип файла: pdf (12480 КБ)
  ✓ Назначение: справочник — нумерация пунктов (312 шт. вида 25.1309)
  ✓ Разбор PDF: страниц 418, найдено пунктов 297, набор «АП-25»
  ✓ Загрузка в базу: 297 пунктов с эмбеддингами (lmstudio:nomic-embed-text)

  ⚠ Пропущено строк оглавления: 46 (это ссылки на пункты, а не сами пункты).
```

То же самое можно сделать мышью: вкладка **«Загрузка»** в веб-интерфейсе
— перетащите файл в окно браузера.

## Главное правило системы

**Решение принимает человек.** Ни один агент не меняет требование и не
проставляет «соответствует». Агент готовит *предложение*, инженер видит
diff «было/стало» и нажимает «Принять» или «Отклонить». Каждое изменение
попадает в историю ревизий с автором и причиной.

Это не перестраховка. Цена ошибки в сертификации — не переписанный
абзац, а недопуск изделия к эксплуатации; на защите перед регулятором
объяснение «так решила модель» не работает.

## Как это выглядит в работе

```
Word/Excel или Teamcenter
        ↓
   staging (сырьё)          ← видно, что именно пришло из документа
        ↓  инженер проверяет в «Мастере импорта»
   requirement (production) ← у каждого: источник, версия, история
        ↓
   агенты: Редактор → Классификатор → Gap-аналитик
        ↓  предложения, а не правки
   инженер: diff → «Принять»
        ↓
   Протокол соответствия (Word/Excel) + запись обратно в Teamcenter
```

## Что уже работает

### Модуль 3.1 — Слой импорта (Hybrid Data Ingestion)

**Режим Б: парсер файлов.** `.docx` и `.xlsx` разбираются **без
python-docx и openpyxl** — стандартной библиотекой (Office-форматы это
zip с XML). Причина практическая: в КБ установка пакетов согласуется
неделями, а импорт нужен в первый день.

**PDF** — единственный формат с внешней зависимостью (`pymupdf` или
`pypdf`): это бинарный формат со сжатием и своими кодировками шрифтов,
стандартной библиотекой его не прочитать. При загрузке PDF система:
* убирает **колонтитулы** — строку, повторяющуюся на большинстве страниц
  (иначе «Авиационные правила Часть 25» попадёт в текст каждого из 300
  пунктов и испортит эмбеддинги);
* убирает **номера страниц** («- 512 -», «Стр. 15 из 400»);
* склеивает **переносы**: `неверо-\nятное` → `невероятное`, иначе поиск
  по слову не найдёт пункт;
* отбрасывает **оглавление** — строки вида `25.1309 Оборудование ..... 512`
  (это ссылки на пункты, а не сами пункты);
* распознаёт **скан** (PDF без текстового слоя) и честно говорит, что
  нужен OCR, вместо того чтобы вернуть пустой результат.

* иерархия заголовков → `section_path` вида `3 Требования > 3.1 Надёжность`
  (по стилю *и* по `outlineLvl` — в выгрузках TC заголовки часто без стиля);
* таблицы атрибутов в двух формах: с шапкой и «ключ-значение»;
* идентификаторы `[REQ-123]`, `REQ-123`, `[ТРБ-77]`, `[SYS-0042]`;
* уверенность разбора для каждой записи — есть ли номер, модальный
  глагол, достаточная длина. **Парсер не додумывает**: решение
  «требование это или пояснение» остаётся за инженером.

**Режим А: коннектор Teamcenter.** Воспроизводит рабочую схему заказчика
один в один: JSON-логин `Core-2011-06-Session/login` → кука сессии →
XML-запрос `getItemAndRelatedObjects` с CDATA. Имя куки не зашито
(`ASP.NET_SessionId` при IIS, `JSESSIONID` при Tomcat).

**Повторный импорт** того же файла распознаётся по sha256 и отклоняется —
типовая ошибка оператора, которая иначе порождает сотни двойников.

### Модуль 3.2 — Агентский слой

| Агент | Что делает | Нужна ли LLM |
|---|---|---|
| **Редактор** | однозначность, измеримость, проверяемость, атомарность формулировки | нет (LLM только для переформулировки) |
| **Классификатор** | подбор пунктов АП-21/АП-25 векторным поиском | нет (LLM только уточняет) |
| **Gap-аналитик** | пять видов «дыр» в покрытии + подсказка MoC | нет |

**Детерминированное ядро — основной режим.** Оценка формулировки
считается словарями и правилами: результат воспроизводим и объясним
построчно, его можно показать регулятору как формальный критерий.
Оценка, меняющаяся от запуска к запуску, для приёмки непригодна.

**Классификатор не может выдумать пункт.** Модель выбирает только из
кандидатов, отобранных векторным поиском; названный ею пункт вне списка
отбрасывается. Без этого модель уверенно «вспоминает» правдоподобные, но
неверные пункты, а такая привязка попадёт в сертификационный базис.

### Модуль 3.3 — Рабочее место инженера

Веб-консоль — один HTML-файл на ванильном JS, без сборки:

* список требований с фильтрами по ответственному, узлу, статусу;
* **индикатор здоровья сертификации** по узлам изделия:
  `0.2·связь с АП + 0.25·MoC + 0.35·доказательство + 0.2·качество`,
  с расшифровкой, что именно закрыть;
* **очередь предложений с пословным diff** и кнопками «Принять» /
  «Отклонить» (ТЗ п.6.2);
* мастер подготовки данных: что распозналось, с какой уверенностью,
  что перенести в базу;
* выгрузка в Word/Excel в один клик.

### Модуль 3.4 — Плагины

* **code_review** — прослеживаемость «требование → код» для DO-178C
  (цели A-4/A-5) и формальные признаки, ограниченные для уровней A/B:
  динамическая память, `goto`, `setjmp`, `eval`, голый `except`,
  функции-гиганты. Языки: C/C++, Ada, Python.
* **report** — сборка «Протокола соответствия».

> **Честно о DO-178C:** стандарт сертифицирует *процесс* разработки, а не
> исходный текст. «Проверить код на соответствие DO-178C» не может ни
> один инструмент. Плагин решает две автоматизируемые подзадачи —
> прослеживаемость и формальные признаки — и не претендует на большее.

### Демо без настройки

```bash
make demo
```

Поднимает временный PostgreSQL, проходит весь путь и печатает каждый
шаг. Это же — дымовой тест конвейера.

### Внешняя модель эмбеддингов (рекомендуется)

Семантический подбор пунктов АП работает настолько хорошо, насколько
хороша модель эмбеддингов. Офлайн-`hash` сравнивает слова; внешняя
модель понимает смысл.

```bash
export SAPS_EMBEDDING_PROVIDER=lmstudio          # или ollama, vllm, openai
export SAPS_EMBEDDING_MODEL=text-embedding-nomic-embed-text-v1.5
export SAPS_EMBEDDING_BASE_URL=http://192.168.1.50:1234/v1
export SAPS_EMBEDDING_API_KEY=                   # для локального обычно не нужен

saps embeddings          # проверить связь и узнать размерность
saps init --auto-dim     # создать схему под эту модель
```

`saps embeddings` покажет, отвечает ли сервер, какой длины вектор он
даёт и совпадает ли это со схемой БД:

```
Провайдер: lmstudio
Модель:    text-embedding-nomic-embed-text-v1.5
Адрес:     http://192.168.1.50:1234/v1

Пробный запрос к серверу…
✓ Модель отвечает, размерность вектора: 768
✓ Совпадает с SAPS_EMBEDDING_DIM=768
```

**Про размерность — важно.** Колонка `vector(dim)` фиксируется при
`saps init` и потом не меняется (ограничение pgvector). Поэтому
размерность выясняется *до* создания схемы: `--auto-dim` спрашивает её
у модели одним запросом. Типичные значения: `nomic-embed-text` — 768,
`bge-m3` — 1024, `text-embedding-3-small` — 1536.

**Если меняете модель на другую** — старые векторы становятся
бессмысленными: они лежат в другом пространстве, и поиск начнёт
возвращать случайные пункты, ничего не сообщая. Пересчитайте:

```bash
saps index --force       # сбросить старые векторы и посчитать заново
```

При загрузке справочника эмбеддинги считаются **пачками по 32** — для
документа на 300 пунктов это 10 запросов вместо 300.

| Провайдер | Адрес по умолчанию |
|---|---|
| `lmstudio`, `local`, `llamacpp`, `vllm` | `http://localhost:1234/v1` |
| `ollama` | `http://localhost:11434/v1` |
| `openai` | `https://api.openai.com/v1` |
| `hash` | офлайн, без сети |

**Запись обратно защищена четырьмя условиями.** Требование уйдёт в
Teamcenter, только если: запись включена в конфиге, у требования есть
`tc_uid`, статус = `approved`, и не осталось необработанных предложений
агентов. Действие пишется в журнал **до** отправки — обрыв связи не
оставит изменение в PDM без следа в САПС.

## Технический стек: чем и почему отличается от ТЗ

ТЗ п.4 предлагает FastAPI + LangChain/CrewAI + React. Реализовано иначе,
и это осознанные решения:

| ТЗ | Реализовано | Почему |
|---|---|---|
| PostgreSQL + pgvector | **как в ТЗ** | Database-First: без DSN система не стартует |
| FastAPI | HTTP на стандартной библиотеке | ноль зависимостей для установки в закрытом контуре; сервисный слой отделён, FastAPI навешивается сверху без переписывания |
| LangChain / CrewAI | своя детерминированная оркестрация | конвейер сертификации обязан быть воспроизводимым; «агент над агентами» непредсказуем и вдвое дороже по токенам |
| React / Streamlit | один HTML-файл | рабочее место инженера не требует сборки и узла Node в контуре КБ |
| python-docx / openpyxl | разбор zip+XML своими силами | установка пакетов в КБ согласуется; форматы стабильны, кода немного |

Единственная обязательная зависимость — **psycopg**. `pgserver` нужен
только для тестов.

### Прослеживаемость — это схема, а не отчёт

У требования есть источник (`source_document` + `staging_record`), полная
история (`requirement_revision`, append-only), связь с пунктом АП
(`requirement_rule_link`), метод подтверждения (`compliance_item`) и
доказательство (`evidence`). Покрытие считается одним SQL-запросом —
цифры в отчёте и на дашборде не могут разойтись.

Staging отделён от production ради одного вопроса, который в сертификации
задают всегда: **«а что было в исходном документе?»** Нормализация
необратима, поэтому сырьё хранится отдельно.

## Ограничения — честно

1. **Справочник АП в поставке — демонстрационная выдержка** (47 пунктов
   АП-25, 18 АП-21: коды и названия). Полные тексты — документы
   Росавиации со своим режимом распространения. Качество работы
   Классификатора прямо зависит от полноты справочника; своя редакция
   загружается через `saps rules load <файл>`.
2. **Офлайн-эмбеддер `hash` сравнивает слова, а не смысл.** Он работает
   всегда и без сети, но синонимов не понимает: «шестерня» и «зубчатое
   колесо» для него разные. Для боевой работы подключите внешнюю модель
   (см. раздел выше) — тогда подбор пунктов АП идёт по смыслу. Шкала
   косинуса у hash другая, поэтому порог у него отдельный
   (`classify_min_score_hash`) — иначе классификатор молчал бы всегда.
   Смена модели требует `saps index --force`: векторы разных моделей
   несопоставимы.
3. **PDF-разбор рассчитан на типовую вёрстку нормативов.** Проверен на
   документах с колонтитулом, оглавлением и нумерацией вида «25.1309
   Название». Многоколоночная вёрстка, врезки и таблицы внутри пунктов
   могут разобраться неточно — после загрузки стоит просмотреть
   результат (`saps rules list --ruleset АП-25`). Сканы без текстового
   слоя не поддерживаются: нужен внешний OCR.
4. **Проверка формулировок — формальная.** Правила ловят
   двусмысленность, отсутствие числа и модального глагола. Понять, что
   требование технически неверно, они не могут.
5. **Запись в Teamcenter — только свойства объекта** (`setProperties`).
   Создание новых объектов, изменение структуры и workflow не
   реализованы: это операции, которые нельзя отлаживать на промышленном
   PDM без согласованной тестовой среды.
6. **Teamcenter проверен на фейковом SOA-сервере**, повторяющем схему из
   примера заказчика. На реальном сервере возможны расхождения в схеме
   ответа — разбор написан «по смыслу» (ищет объекты с uid/type), а не по
   жёсткому XPath, чтобы пережить смену версии.
7. **Нет разграничения прав пользователей.** Есть журнал действий с
   указанием актора, но кто угодно с токеном может принять любое
   предложение. Обходной путь на сегодня — доменная аутентификация на
   обратном прокси (пример nginx в QUICKSTART.md) и разные токены для
   разных контуров. Полноценные роли — следующий шаг.
8. **Агенты работают синхронно.** Прогон по тысяче требований займёт
   минуты и держит HTTP-запрос открытым. Для таких объёмов запускайте
   агентов из CLI (`saps agent classifier`), а не из веб-интерфейса;
   фоновая очередь — следующий шаг, схема к ней готова.

## Готовность к эксплуатации

Что сделано для промышленной установки (подробности — QUICKSTART.md):

| | |
|---|---|
| Развёртывание | Docker Compose (PostgreSQL с pgvector + приложение) и systemd-юнит |
| Миграции схемы | версионирование, `saps migrate`, блокировка от одновременного запуска нескольких инстансов |
| Совместимость | сервер отказывается стартовать на несовместимой схеме (код 3), а не падает в рантайме |
| Пробы | `/health` (liveness, не трогает БД), `/ready` (база + схема + pgvector), `/metrics` (Prometheus) |
| Обрыв БД | автоматическое переподключение — плановое обслуживание PostgreSQL не требует рестарта САПС |
| Остановка | SIGTERM обрабатывается, текущие запросы доигрывают |
| Логи | stdout, уровни, JSON-режим для сборщиков; пробы мониторинга не засоряют журнал |
| Копии | `saps backup` (pg_dump с расширением vector — проверено реальным восстановлением) |
| Безопасность | контейнер не от root, порт только на localhost, секреты не попадают в образ |

Проверено не на словах: тест `test_prod.py` поднимает сервер, обрывает
все соединения с базой, шлёт SIGTERM и восстанавливается из копии в
чистую базу.

## Дорожная карта (ТЗ п.5)

* **Этап 1 (MVP)** — готово: БД, парсер Word/Excel, интерфейс просмотра.

  отчёты о покрытии.

создание объектов в Teamcenter, анализ чертежей и весовых лимитов
(плагины по ТЗ п.2.4).
