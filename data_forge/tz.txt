# Техническое задание: платформа DataForge

> **Версия:** 1.0 (консолидированная)
> **Назначение документа:** ТЗ для команды ИИ-агентов на разработку MVP промышленной платформы интеграции корпоративных данных, наведения в них порядка и оркестрации сквозных процессов для предприятия с множеством разрозненных информационных систем и «грязными» несостыкованными данными. Документ структурирован так, чтобы каждый раздел можно было передать отдельному агенту как самостоятельную задачу с чёткими границами и критериями приёмки.

---

## 1. Общее описание продукта

**Название:** **DataForge** — платформа интеграции корпоративных данных, наведения в них порядка и оркестрации сквозных процессов.

**Одна фраза:** DataForge подключается ко всем информационным системам предприятия, приводит разрозненные и грязные данные к единой достоверной модели и на её основе автоматизирует и контролирует производственные и бизнес-процессы, а встроенный AI-ассистент помогает как развернуть платформу, так и эксплуатировать её.

**Философия продукта:** это **операционная платформа**, а не аналитический дашборд. Решения превращаются в действия: обратная запись в системы-источники, задачи людям, автоматические сценарии. Приоритеты — надёжность, прослеживаемость (lineage) и качество данных. Простота достигается не урезанием возможностей, а строгой модульностью: каждый компонент решает одну задачу хорошо, но при этом вся платформа собирается в **один образ приложения** (модульный монолит), чтобы не плодить преждевременную сложность.

### 1.1. Контекст предприятия (проблемы, которые решаем)

| Проблема | Как проявляется | Ответ DataForge |
|----------|-----------------|-----------------|
| **Много разных ИС** | 1С (ERP), Teamcenter (PLM), MES, WMS, CRM, легаси-БД, Excel-файлы, оборудование/IoT | Универсальный слой коннекторов + единый каталог |
| **Грязные данные** | Дубли, опечатки, разные единицы, пустые поля, конфликтующие значения | Движок качества данных (профилирование, правила, очистка, карантин) |
| **Несостыкованные данные** | Один контрагент/деталь/заказ по-разному в 5 системах | Мастер-данные (MDM) + вероятностный матчинг и дедупликация |
| **Ручные процессы** | Согласования по почте, ручной перенос данных между системами | Оркестратор процессов + обратная запись (write-back) |
| **Нет единой картины** | Никто не видит сквозной статус заказа/производства | Единая семантическая модель (Ontology) |
| **Сложность запуска и эксплуатации** | Много систем — трудно настроить и сопровождать | AI-надстройка (Copilot) для развёртывания и эксплуатации |

### 1.2. Целевые кейсы (must-have для MVP)

| # | Кейс | Что демонстрирует |
|---|------|-------------------|
| K1 | **Единая точка правды по сущности** | Сборка «золотой записи» контрагента/детали/заказа из N систем с разрешением конфликтов |
| K2 | **Очистка и контроль качества данных** | Профилирование источника → правила качества → отчёт, автоочистка и карантин |
| K3 | **Сквозной процесс с обратной записью** | Расхождение остатков ERP↔WMS → задача ответственному → корректировка → write-back в источник |
| K4 | **Прослеживаемость (data lineage)** | По любому значению видно, откуда оно пришло и как было преобразовано |
| K5 | **Мониторинг производства/операций** | Единая панель сквозного статуса заказов/операций поверх интегрированных данных |
| K6 | **AI-ассистент** | Помощь в подключении источников/настройке правил (setup) и ответы/диагностика в эксплуатации (ops) |

Слои данных (medallion): **Bronze** (сырые как есть) → **Silver** (очищенные, типизированные) → **Gold** (согласованные бизнес-сущности для потребления).

> **Принцип упаковки:** все модули (`Connect Hub`, `Quality`, `MDM`, `Ontology`, `Orchestrator`, `Catalog`, `AI`) — это Python-пакеты в едином дереве, собираемые в **один образ**. Отдельные контейнеры — только у инфраструктуры (PostgreSQL, Redpanda, Temporal, Keycloak, Dagster) и, опционально, у AI-провайдера.

### 2.1. Рекомендуемый стек

| Слой | Технология | Обоснование |
|------|-----------|-------------|
| Backend (единый образ) | **Python 3.12 + FastAPI** | Асинхронность, автогенерация OpenAPI, читаемость |
| Оркестрация пайплайнов данных | **Dagster** | Data-aware оркестратор, встроенный lineage, asset-модель |
| Оркестрация бизнес-процессов | **Temporal** | Надёжные долгоживущие процессы, ретраи, human-in-the-loop |
| Хранилище (Lakehouse) | **PostgreSQL + Apache Iceberg / DuckDB** | Простота для MVP, миграция в масштаб позже |
| Реляционная БД (метаданные, MDM) | **PostgreSQL 16** | RLS, JSONB, надёжность |
| Потоки/CDC | **Debezium + Redpanda** (Kafka-совм.) | CDC из легаси-БД без нагрузки на источник |
| Качество данных | **Great Expectations + Polars/Pandas** | Декларативные правила, автоотчёты |
| Матчинг/дедупликация | **Splink** | Вероятностный record linkage промышленного уровня |
| Каталог/lineage | **OpenMetadata** (или собственный на PG) | Каталог, lineage, glossary |
| Frontend | **React + TypeScript + Vite**, графики **Recharts** | Стандарт, много примеров |
| Auth | **Keycloak** (OIDC, RBAC/ABAC) | Готовые роли и интеграция |
| AI-надстройка | **LLM через провайдер-агностичную абстракцию** (в т.ч. локальные/on-prem) | Промышленная/изолированная среда |
| Инфраструктура | **Docker Compose** (MVP) → Helm/K8s | `docker compose up` поднимает всё |
| CI/CD | **GitHub Actions + Docker** | Воспроизводимый пайплайн |

> **Правило для агентов:** не вводить новую технологию без ADR (Architecture Decision Record). Предпочитать конфигурацию существующих инструментов написанию своих.

## 3. Ключевые концепции продукта

### 3.1. Коннекторы (Connect Hub)
Единый механизм подключения источников с тремя режимами приёма:
- **Batch** — периодическая выгрузка (файлы, SQL-дампы, API).
- **CDC** — захват изменений из БД через Debezium (без нагрузки на источник).
- **Stream** — потоковые данные (IoT/оборудование, шина событий).

Все коннекторы реализуют **единый интерфейс** `Connector` (см. §5.1), чтобы платформа не знала о специфике источника. Добавление нового источника — декларативный конфиг + при необходимости трансформация, без переписывания ядра.

### 3.2. Семантическая модель (Ontology)
Бизнес-язык поверх сырых таблиц: объекты (`Контрагент`, `Деталь`, `Заказ`, `ПроизводственнаяОперация`, `Партия`), их атрибуты, связи и **actions** (действия, которые можно над ними выполнять — например «скорректировать остаток», «согласовать»). Пользователи и процессы работают с Ontology, а не с сырыми таблицами.

### 3.3. Мастер-данные (MDM) и матчинг
Сборка «золотой записи» из нескольких источников:
- Правила приоритета источников (survivorship).
- Вероятностное сопоставление дублей и вариантов написания.
- Ручное подтверждение спорных случаев (stewardship-очередь).

### 3.4. Обратная запись (Write-back) — обязательное свойство
Платформа не только читает, но и **пишет обратно** в системы-источники результаты процессов (через API/коннектор), с гарантией идемпотентности и полным аудитом. Это отличает операционную платформу от аналитической.

### 3.5. Прослеживаемость (Lineage)
Для любого значения в Gold-слое доступна полная цепочка: источник → трансформации → правила качества → золотая запись. Строится автоматически оркестратором.

### 3.6. AI-надстройка (Copilot)
Ассистирующий слой поверх платформы, работающий через инструменты (function calling) над публичными API. Не имеет собственного «скрытого» доступа к данным, действует в рамках RBAC/RLS пользователя, всё логируется. Помогает на двух стадиях: **развёртывание/настройка** и **эксплуатация**. Модуль полностью отключаем без влияния на ядро.

- `AuditLog` и `AiInteraction` неизменяемы (append-only).

## 5. Функциональные требования по модулям

### 5.1. Connect Hub (интеграция источников)

**Единый контракт коннектора:**
```python
class Connector(Protocol):
    def discover(self) -> list[DatasetSchema]: ...
    def read_full(self, dataset: str) -> Iterator[Record]: ...
    def read_changes(self, dataset: str, cursor: Cursor) -> ChangeBatch: ...
    def write_back(self, records: list[WriteRecord]) -> WriteResult: ...
```

- **FR-1.1:** Реестр источников; добавление источника декларативным конфигом.
- **FR-1.2:** Три режима приёма: batch, CDC (Debezium), stream.
- **FR-1.3:** Приём файлов CSV/Excel/JSON/XML и подключение к SQL-источникам (PostgreSQL, MySQL, MSSQL, Oracle — минимум 2 в MVP).
- **FR-1.4:** Инкрементальная загрузка, устойчивость к недоступности источника (ретраи, backoff).
- **FR-1.5:** Автоматическое профилирование схемы при подключении.

#### Коннектор `onec_odata` (1С:Предприятие через стандартный OData)

| Возможность | Реализация | FR |
|-------------|-----------|-----|
| Обнаружение сущностей | GET `.../standard.odata/$metadata` (EDMX) → автопрофилирование справочников/документов/регистров | FR-1С.1 |
| Полная выгрузка | GET `.../standard.odata/<Entity>?$format=json` с пагинацией (`$top`/`$skip`) | FR-1С.2 |
| **Инкремент (CDC-подобный)** | Через план обмена: POST `SelectChanges` (atom-feed изменений и удалений) + `NotifyChangesReceived` для подтверждения курсора. Fallback: `$filter` по дате изменения | FR-1С.3 |
| Выбор/фильтрация | `$select`, `$filter`, `$expand` для раскрытия ссылок | FR-1С.4 |
| **Write-back** | PATCH/PUT с `If-Match: <DataVersion>` (оптимистичная блокировка, обработка `412`); проведение документов через `/Post`; массовая загрузка с заголовком `1C_OData-DataLoadMode: true` | FR-1С.5 |
| Аутентификация | Basic/token к опубликованному OData-эндпоинту | FR-1С.6 |

> Конфиг: `base_url`, креды, список сущностей, стратегия инкремента (`exchange_plan` / `filter_by_date`), маппинг в Bronze
