# Тесты, патчи, векторы, маршрутизация, история

Пять последних пунктов из плана развития. Как и прежде: обязательных
зависимостей ноль, каждая критичная проверка подтверждена диверсией.

```bash
python3 -m agent -P coder    "почини падающий тест"
python3 -m agent -P reviewer "разбери, что сделано в src/"
python3 -m agent -P ops      "почему кончается память"
python3 -m agent --runs                 # история прогонов
python3 -m agent --runs 7               # подробности прогона №7
```

## 1. `dev` — прогон тестов и точечная правка

| инструмент | что делает |
|---|---|
| `run_tests` | прогнать тесты и показать **только упавшее** |
| `apply_patch` | правка дифом или по номерам строк |

### run_tests

Вывод pytest на большом проекте — тысячи строк, из которых важны
двадцать. Остальное вытесняет из окна саму задачу. Инструмент отдаёт
упавшее плюс итог; полный вывод — по запросу `full=true`.

Сам находит, чем прогонять: цель `test` в Makefile → pytest → файлы
`tests/test_*.py`. Не нашёл — честно отказывается, а не молчит.

**Провал определяется двумя способами: по коду возврата И по тексту.**
Самописные прогонщики сплошь и рядом возвращают 0, печатая
«провалено: 2». Диверсия «смотреть только на код возврата» уронила
4 проверки.

**Пустой вывод не считается успехом.** Это «прогонщик не запустился», а
не «всё хорошо».

### Дефект, найденный живьём

Агент починил функцию, а тест продолжал падать с прежней ошибкой.
Причина: Python считает `.pyc` устаревшим по паре «время правки +
**размер** исходника». Замена `w + h` на `w * h` размер не меняет, обе
операции укладываются в одну секунду — и выполняется старый код.

Хуже всего то, что виноватым выглядел патч, хотя файл был исправлен
верно. Теперь `run_tests` сносит `__pycache__` перед прогоном.
Закрыто тестом: правка, не меняющая длину строки, обязана попасть в
прогон.

### apply_patch

`edit_file` требует уникального фрагмента и отказывается, если текст
встречается дважды, — модели на этом буксуют, повторяя одну попытку.
Здесь два запасных пути:

- **унифицированный диф** `@@ -10,3 +10,4 @@`;
- **номера строк**: `start_line`, `end_line`, `replacement`
  (пустой `replacement` удаляет строки).

Наложение дифа своё: в стандартной библиотеке есть только построение
(`difflib`). Номера строк в заголовке `@@` считаются подсказкой — модели
в них часто ошибаются, а контекстные строки копируют верно, поэтому
участок ищется по содержимому рядом. Не нашёлся — **отказ**, файл не
портится.

## 2. Векторы в SQLite (`semantic`)

Полнотекстовый поиск не находит «как закрепить деталь», если записано
«крепление узла болтами». PostgreSQL это решает, но ставить его ради
пяти тысяч записей на сервере с гигабайтом — перебор.

| инструмент | что делает |
|---|---|
| `index_memory` | построить векторы для фактов |
| `semantic_recall` | найти по смыслу |
| `smart_recall` | оба поиска сразу, с пометкой источника |
| `vector_status` | сколько векторов, сколько памяти |

Хранение — `array('f').tobytes()` в BLOB, вчетверо компактнее JSON.
Векторы нормализованы, поэтому близость это просто скалярное
произведение.

Замерено тестом, а не прикинуто:

| записей × размерность | память | поиск |
|---|---|---|
| 5000 × 384 | **7.3 МБ** | доли секунды |
| списки Python, 50k × 384 | процесс убит | — |

Выше 5000 записей инструменты честно предупреждают: пора на PostgreSQL
(навык `pg`).

**Векторы разной размерности не сравниваются.** Разные модели дают
разные пространства; сравнение дало бы случайное число, похожее на
осмысленное. Диверсия это проверяет.

Служба векторов недоступна — `smart_recall` продолжает искать словами и
говорит об этом, а `semantic_recall` отказывается явно. Пустой ответ,
который модель примет за «ничего нет», недопустим.

## 3. Маршрутизация моделей

```json
"model_cheap": "qwen2.5:7b",
"model_strong": "devstral-small-2:22b",
"route_long_context": 12000
```

Снаружи `Router` неотличим от одной модели, поэтому ядро агента о нём
не знает и менять его не пришлось.

Выбор — по признакам запроса, без гадания:

| условие | модель |
|---|---|
| в задаче `[сложно]` / `[просто]` | как указано — сильнее всего |
| контекст длиннее порога | сильная (дешёвые теряют нить) |
| в последних результатах инструментов ОШИБКА | сильная |
| иначе | дешёвая |

Деньги считаются по каждой модели отдельно, в отчёте видно экономию:

```
дешёвая gpt-4o-mini: вызовов 34, токенов 210,400, $0.0421
сильная gpt-4o:      вызовов 6,  токенов 48,200,  $0.2410
выбор: рутинный шаг — 34; в последних шагах была ошибка — 4; …
экономия против только сильной: ~$0.4832
```

## 4. История прогонов

Данные копились в базе с самого начала, но смотреть их было нечем.

```bash
python3 -m agent --runs        # список
python3 -m agent --runs 7      # план, расход, журнал прогона
```

Показывает состояние, время, шаги, токены, деньги, роль; для одного
прогона — весь план с отметками (включая `[?]` — ждёт ответа человека)
и журнал событий.

## 5. Профили `ops` и `reviewer`

**`ops`** — диагностика сервера, **строго только чтение**. Ставить
пакеты, править конфиги, перезапускать службы и чистить логи запрещено
промптом: нашёл причину — опиши и предложи команду человеку. Помнит,
что сервер маленький: никаких `find /` по всему диску.

**`reviewer`** — второй проход по чужой работе отдельным прогоном.
Ищет расхождение описания с кодом, молчаливые сбои, проверки, которые
не могут провалиться. Делит замечания на ОШИБКА / РИСК / ЗАМЕЧАНИЕ и
не выдаёт стиль за ошибку. Ничего не правит — его результат список, а
не патч.

## Тесты

```bash
python3 tests/test_dev.py     # 73 проверки
make test                     # 748 проверок
```

| что ломали | что упало |
|---|---|
| провал определяется только по коду возврата | 4 |
| пустой вывод считается успехом | 1 |
| кэш `.pyc` не чистится перед прогоном | 2 |
| несовпадающий диф применяется как есть | 2 |
| векторы разной размерности сравниваются | 1 |
| маршрутизатор всегда берёт дешёвую | 2 |
| сбой службы векторов возвращает пустоту | 1 |

Сквозной прогон на живом агенте: тест упал → агент прочитал код →
починил `apply_patch` → тест прошёл. Автоснимок `vcs` при этом
зафиксировал состояние до правки.
