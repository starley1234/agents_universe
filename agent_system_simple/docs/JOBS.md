# Поставил и забыл

Раньше работа жила ровно столько, сколько открыт терминал: закрыл SSH —
прогон умер. Поставить задачу на ночь было нельзя.

Теперь задание кладётся в очередь, а работает **фоновый исполнитель**.
Он переживает выход пользователя, закрытие браузера и — под systemd —
перезагрузку сервера.

```bash
python3 -m agent --job "разобрать договоры из in/ и собрать реестр" \
                 --hours 6 --notify boss@firma.ru
# Задание #1 принято
#   выбран профиль «docs» — совпали признаки темы
#   бюджет: 6.0 ч, сообщу на boss@firma.ru
# Можно закрывать терминал.

python3 -m agent --jobs          # что происходит
python3 -m agent --jobs-stop 1   # снять
```

В вебе то же самое — вкладка **«Задания»** открывается первой: поле для
задачи, бюджет, куда сообщить. Список сам обновляется каждые 5 секунд,
работающее задание помечено пульсирующей точкой.

## Установка на сервер

```bash
sudo cp deploy/agent-worker.service deploy/agent-web.service \
        deploy/agent-backup.service deploy/agent-backup.timer \
        /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now agent-worker agent-web agent-backup.timer

systemctl status agent-worker
journalctl -u agent-worker -f      # смотреть работу
```

Юниты читают `/opt/agent_system/.env`, перезапускаются сами
(`Restart=always`) и поднимаются после перезагрузки. Память исполнителя
ограничена 512 МБ: на сервере с гигабайтом без предела один прогон
может забрать всё.

`agent-backup.timer` раз в сутки делает копию базы через
`sqlite3.backup` — обычный `cp` во время записи даёт битый файл. Хранит
14 последних.

## Упорство: подход — не приговор

Первая версия очереди бросала работу, если та не влезла в отведённое
время: `--hours 2` кончились на втором пункте из пяти — задание
помечалось «ошибка», и всё. «Поставил и забыл» превращалось в
«поставил и проверяй».

Теперь исход подхода различается по существу:

| чем кончился подход | что делает система |
|---|---|
| план выполнен | готово, зовёт человека |
| вышло время, деньги, итерации | **продолжает следующим подходом** |
| агент забуксовал, тупик в плане | продолжает, но с паузой |
| ждёт ответа человека | останавливается: без ответа смысла нет |

Продолжение идёт **тем же прогоном** (`--resume`), а не с нуля: план,
сделанные пункты и память остаются. Иначе каждый подход заново
планировал бы и делал первые шаги.

```
↻ #1 подход окончен (time), сделано 2/6 — продолжу
↻ #1 подход окончен (time), сделано 4/6 — продолжу
✔ #1 done
```

**Упорство не бесконечно.** Два ограничителя:

- **предел подходов** (`--rounds`, по умолчанию 20). Исчерпан — задание
  честно помечается провалившимся с причиной;
- **пауза без продвижения** (60 с). Если за подход не прибавилось
  сделанных пунктов, следующий начнётся не сразу. Сравнивается ЧИСЛО
  закрытых пунктов, а не строка: первый подход даёт «0/3» против
  пустого значения — формально «изменилось», хотя не сделано ничего.

## Что происходит, когда за системой не смотрят

Очередь писалась исходя из того, что человек ушёл. Значит, важно не
«задание выполнилось», а что система переживает всё остальное.

**Исполнитель умер** — сервер перезагрузили, процесс убили. Задание
осталось бы в «running» навсегда: человек думает, что работа идёт, а её
нет. Поэтому исполнитель раз в минуту отмечается живым, и задание без
отметки дольше 5 минут возвращается в очередь.

**Задание роняет исполнителя.** После трёх попыток оно помечается
провалившимся с причиной: дело в нём самом, а не в случайном сбое.
Иначе очередь крутит один и тот же сломанный прогон вечно.

**Два исполнителя на одну очередь.** Взятие задания атомарно:
`UPDATE ... WHERE status='queued'` одной операцией. Проверено тестом с
барьером — восемь потоков читают очередь, потом одновременно пишут;
побеждает один. Без этого условия работа выполнилась бы восемь раз.

**Человек передумал.** Снятие из веба замечается между шагами, прогон
прекращается, а не доигрывает до конца.

**Работа закончилась.** Смысл затеи в том, чтобы забыть — а забыть
можно, только если система сама позовёт. `--notify` шлёт итог на почту
или в мессенджер. Почта не настроена — письмо ляжет черновиком в
`outbox/`, и об этом будет сказано, а не «тихо ничего».

Тест на гонку сначала **не ловил** дефект: SQLite сериализует запись, и
потоки успевали по очереди. Настоящая гонка — когда все уже прочитали
очередь, а пишут одновременно; воспроизводится барьером.
