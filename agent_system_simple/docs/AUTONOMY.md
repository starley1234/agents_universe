# Автономный режим: часы работы без человека

## Запуск

```bash
python3 -m agent --auto -P cad_auto --hours 8 \
  "оптимизировать планетарный редуктор: минимум габарит при i=20"

# прервали или упало питание — продолжаем с того же места
python3 -m agent --auto --resume 3
```

Всё состояние в одном файле `agent.db` (SQLite, stdlib). Прогон
переживает перезапуск процесса и сервера.

---

## Почему одиночного цикла не хватало

Четыре вещи ломают агента на длинной дистанции. Каждая решена отдельно.

### 1. Цель забывается

История обрезается по объёму, и через час в окне остаются последние
вызовы инструментов — а зачем всё начиналось, модель уже не видит.

**Решение:** цель и текущий пункт плана подставляются в **каждую**
итерацию заново, из базы. История одной итерации в следующую не тащится.

Это главный риск, поэтому он покрыт отдельным тестом: проверяется, что
текст цели физически присутствует в каждом рабочем промпте. При
искусственном отключении подстановки тест падает.

### 2. Зацикливание

Модель повторяет один и тот же вызов до конца бюджета.

**Решение:** подпись действия `sha1(имя + аргументы)`. Три одинаковых
подписи подряд — в промпт добавляется прямое указание сменить подход.
Плюс сигнал `stuck` от рефлексии: три подряд — прогон останавливается,
не выжигая оставшиеся часы.

### 3. Контекст кончается

**Решение:** каждая итерация — свежий короткий контекст: цель, пункт
плана, выжимка из памяти по теме пункта, последние 6 действий.
Не растущая простыня.

### 4. Нет накопления знаний

Без памяти агент на 20-й итерации исследует то же, что на 3-й.

**Решение:** после каждой итерации — рефлексия. Модель возвращает JSON
`{"learned": [...], "next": "...", "stuck": false}`, факты уходят в
базу. Перед работой агент вызывает `recall` и видит, что уже известно.

## Декомпозиция: шаги, исполнители, порядок

```bash
agent --auto --decompose "собрать комплект документов по редуктору"
agent --do "…"                    # в простом режиме включено само
```

Обычный план — плоский список строк, и порядок в нём просто нумерация.
Это ломается предсказуемо: пункт «собрать отчёт» берётся раньше
«посчитать данные», агент честно пишет отчёт ни о чём, и человек
замечает это последним.

С `--decompose` планировщик возвращает не строки, а структуру:

```
План:
  1. измерить зазоры в редукторе по STL [cad]
     проверка: числа зазоров в мм
  2. посчитать запас прочности по замерам [coder] ← после 1
     проверка: коэффициент запаса
  3. оформить отчёт о приёмке в docx [office] ← после 1, 2
     проверка: файл otchet.docx
```

Три поля на каждый шаг:

| поле | зачем |
|---|---|
| **кто** | исполнитель из списка профилей с описаниями |
| **после** | номера шагов, без которых этот не сделать |
| **проверка** | чем подтвердится выполнение |

### Что это меняет в работе

**Пункт берётся по готовности, а не по номеру.** `next_ready_task`
пропускает шаги с незакрытыми зависимостями. Пока «измерить» не
сделано, «оформить отчёт» не возьмётся, даже если стоит следующим.

**Исполнитель из плана важнее догадки диспетчера.** Планировщик видел
задачу целиком, диспетчер — одну строку. Если план назначил `office`
пункту «почини тест», выполнять будет `office`.

**Результаты зависимостей попадают в контекст.** Исполнитель шага 3
видит, что дали шаги 1 и 2, и не добывает заново уже добытое. Плюс
получает строку «чем подтвердить выполнение».

### Второй уровень: подшаги

Планировщик видит задачу до начала работы и ошибается в масштабе:
пункт «подготовить комплект документов» на деле оказывается тремя
разными работами. Раньше у исполнителя было два выхода — тянуть
неподъёмное целиком или провалить пункт. Оба плохие.

Теперь есть третий: инструмент `plan_split`.

```
── итерация 1 · #1 подготовить комплект документов
→ передано агенту «office» (назначен планом)

⑂ пункт разбит на подшаги: подготовить комплект документов
── итерация 2 · #3 написать пояснительную записку
── итерация 3 · #4 собрать таблицу замеров

✓ пункт закрыт целиком: подготовить комплект (подшагов: 2 из 2)
── итерация 4 · #2 отправить комплект заказчику
```

Правила, без которых это ломается:

**Разбиение — не выполнение.** Пункт возвращается в план как
незакрытый: работа только распланирована, к ней ещё не приступали.
Закрыть его в этот момент значило бы объявить сделанным то, чего нет.

**Родитель сам в работу не идёт** — работают его подшаги. Иначе агент
делал бы работу дважды: сначала крупный пункт целиком, потом его же
по частям.

**Родитель закрывается сам,** когда подшаги закончились. Провалился
хоть один — родитель тоже проваленный, и в результате написано, какой
именно подшаг не вышел.

**Глубже двух уровней нельзя.** Подшаг разбить уже не получится:
инструмент откажет. Иначе прогон уходит в дробление вместо работы.
Не больше 6 подшагов за раз, повторно разбить нельзя.

**План читается деревом:** подшаги идут сразу за своим родителем с
отступом, а не сваливаются в конец списка.

### Когда план невыполним

Провалилась зависимость или планировщик замкнул кольцо — прогон не
делает вид, что всё нормально:

```
⛔ невыполнимые пункты (зависимость провалена или зациклена):
   · оформить отчёт по данным

Прогон #1: deadlock
НЕ ВЫПОЛНЕНЫ (зависимость провалена или зациклена):
  #2 оформить отчёт по данным
```

Такие пункты помечаются `skipped` с причиной, а не остаются молча
«открытыми». Кольцо, найденное сразу после планирования, снимается
автоматически — работать по порядку лучше, чем встать целиком.

### Что если модель не осилила JSON

Откат к плоскому списку с предупреждением. Выдумывать структуру или
получать план из одного пункта — хуже, чем честно спланировать проще.

### Старые базы

В таблицу `task` добавлены три колонки. `CREATE TABLE IF NOT EXISTS` их
не создаст — таблица уже есть, поэтому при открытии базы выполняется
миграция `ALTER TABLE`. Существующие прогоны и планы сохраняются.

## Цикл

```
цель
 ↓
планировщик → 3-7 проверяемых пунктов в базу
 ↓
┌─ взять пункт из базы
│  собрать контекст: цель + пункт + память + недавние действия
│  агент работает инструментами
│  plan_done / plan_fail
│  рефлексия → факты в память
└─ повторить

останов: план выполнен | вышло время | лимит итераций | застой
```

---

## Что хранится

Один файл SQLite, четыре сущности — больше не нужно.

| таблица | назначение |
|---|---|
| `fact` + FTS5 | семантическая память, полнотекстовый поиск |
| `entity` / `relation` | **онтология**: объекты и связи |
| `task` | план, переживающий перезапуск |
| `event` | эпизодическая память, подписи для детектора повторов |
| `run` | прогон: статус, шаги, расход контекста |

### Онтология не зашита в код

Типы объектов и предикаты придумывает сам агент по ходу работы:

```
part:водило --вращается_внутри--> part:венец
part:фланец --из_материала--> material:PETG
idea:оффер3 --опирается_на--> metric:конверсия
```

Поэтому одна схема обслуживает и редуктор, и маркетинг. Дубликаты
отсекаются на уровне БД: `UNIQUE(kind,name)` и `UNIQUE(subj,pred,obj)`.

## Инструменты памяти

| инструмент | зачем |
|---|---|
| `remember` / `recall` | записать вывод / найти ранее найденное |
| `note_entity` / `link` / `describe` | объекты и связи графа |
| `plan_add` / `plan_show` / `plan_done` / `plan_fail` | план |

Ключевое в промпте профиля: **тупик — тоже результат**. Агент обязан
записать его через `remember` и закрыть пункт через `plan_fail`, а не
долбить одно и то же.

## Расход токенов на длинном прогоне

Складывается из трёх мер:

- контекст итерации короткий и не растёт (см. пункт 3);
- результаты инструментов обрезаются, старые сворачиваются — **−74 %**;
- локальная модель на GPU-сервере: токены бесплатны, платит электричество.

Для суток работы это принципиально: на OpenRouter сутки непрерывной
работы стоили бы заметных денег, на локальной Devstral — нет.

Расход виден в базе: `run.chars_sent`.

## Перепланирование

Плохой план чинится, а не дорабатывается до конца бюджета. Триггеры:

- накопилось 2 провала (`replan_after_fails`);
- агент буксует два цикла подряд.

Планировщик получает: цель, что **сделано**, что **провалено**, что
осталось — и составляет новый план оставшейся работы. Выполненное и
проваленное сохраняется как история, убираются только невыполненные
пункты. Факт пересмотра пишется в память.

Ограничение: не больше 3 пересмотров за прогон, иначе агент будет
бесконечно перепланировать вместо работы.

## Ограничения, честно
- Рефлексия — это ещё один вызов модели на итерацию, +15-20 % токенов.
  Окупается тем, что агент не ходит по кругу.
- Параллельных агентов нет. Один прогон — один процесс. Несколько
  запускаются просто разными командами с разными `--db`.
