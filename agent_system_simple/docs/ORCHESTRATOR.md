# Оркестратор: кого подключить дальше

```bash
python3 -m agent --auto --decompose --orchestrate "цель"
python3 -m agent --do "цель"        # включён сам
python3 -m agent --job "цель"       # в очереди тоже
```

## Что было

План составлялся ОДИН раз, до начала работы, исполнители назначались
заранее. Дальше система шла по списку механически: пункт выполнен —
берём следующий, что бы в нём ни оказалось. Знание, добытое на третьем
шаге, никак не влияло на четвёртый.

## Что теперь

Оркестратор смотрит на результат шага и решает:

| решение | когда |
|---|---|
| **дальше** | план в порядке, не мешаем |
| **сменить** | шаг провалился, потому что достался не тому агенту |
| **добавить** | вскрылась работа, которой не было в плане |
| **проверить** | результат сомнителен, нужен второй агент на сверку |
| **пропустить** | пункты потеряли смысл после того, что узнали |
| **закончить** | цель достигнута, остальное лишнее |

```
── итерация 3 · #3 оформить отчёт о приёмке
→ передано агенту «office» (назначен планом)

⚙ оркестратор: добавить шагов: 1 — замеры на границе допуска, нужна сверка
   + сверить замеры с паспортом изделия

── итерация 4 · #4 сверить замеры с паспортом изделия
→ передано агенту «verify»
```

В итоге прогона видно, что он делал:
`оркестратор вмешивался 1 раз, добавил шагов: 1`.

## Два принципа

**Решает модель, но в рамках.** Что делать дальше — суждение, правилами
его не заменить. Но каждое решение ограничено, и ограничения проверяются
в коде, а не просьбой в промпте: модель их нарушает, а последствия
необратимы.

| ограничение | зачем |
|---|---|
| смена исполнителя — 2 раза на пункт | дальше дело не в исполнителе, а в пункте |
| добавление — до 3 шагов за раз | иначе план растёт быстрее, чем выполняется |
| рост плана — не больше исходного | оркестратор не должен работать вместо агентов |
| выдуманный агент | отвергается: пункт ушёл бы в никуда |
| смена на того же агента | отвергается: пустая трата подхода |
| нечитаемый ответ | работаем по плану, а не «додумываем» решение |

**Вмешивается не всегда.** Спрашивать после каждого шага дорого, а при
нормальном ходе ответ всегда «дальше». Повод определяется правилами —
они дёшевы и воспроизводимы:

- шаг провалился;
- результат подозрительно пустой (короче 40 знаков);
- агент топчется на месте;
- пройдена каждая третья задача.

## Что видно человеку

Оркестратор бесполезен, если его решений не видно: работа идёт иначе,
чем в плане, а почему — непонятно. Поэтому он на виду в трёх местах.

**В карточке задания** (веб и `--jobs`) — кто работает прямо сейчас,
на каком шаге и что решил оркестратор:

```
#1  работает  собрать комплект документов по редуктору
    роль office, прогон #1, отклик 3 с назад
    ▶ coder · посчитать нагрузку  (1/3)
    ⚙ оркестратор: добавить: замеры на границе допуска — нужна сверка
```

Обновляя страницу, видно, как работа переходит от агента к агенту:

```
running │ cad    │ измерить зазоры    │ 0/3
running │ coder  │ посчитать нагрузку │ 1/3
running │ office │ оформить отчёт     │ 2/3 │ ⚙ добавить: нужна сверка
done    │        │                    │ 3/3
```

**В журнале прогона** решения выделены цветом, а не теряются среди
вызовов инструментов.

**В итоге прогона** — сводка: `оркестратор вмешивался 3 раза,
добавил шагов: 1, сменил исполнителя: 1`.

## Границы честно

**Оркестратор не всесилен.** Он видит план, результат шага и известные
факты — но не содержимое файлов и не ход рассуждения агента. Решение
принимается по отчёту, а отчёт может врать.

**Стоит денег.** Каждое вмешательство — вызов модели с планом в
контексте. На длинном прогоне это заметная доля расхода, поэтому
триггеры настроены сдержанно.

**Без модели молчит.** Не настроен или недоступен — работа идёт строго
по плану, как раньше. Прогон из-за этого не встаёт.
