# agents_universe

Четыре независимых проекта об автономных агентах: от одиночного агента с
инструментами до прикладной системы сертификации авиатехники.

**Общего кода между ними нет.** Каждый ставится, запускается и
версионируется отдельно; ни один не импортирует соседа в рантайме. Общая
у них философия (см. ниже), а не библиотека — это осознанное решение:
общий слой связал бы проекты с разными сроками жизни и разными
требованиями к надёжности.

| Проект | Про что | Зависимости | Тесты |
|---|---|---|---|
| [`agent_system`](agent_system/) | Один автономный агент с инструментами: читает и правит файлы, запускает команды, проверяет результат | нет (ядро на stdlib) | 896 |
| [`multi_agent_system_ontology`](multi_agent_system_ontology/) | Несколько агентов-личностей, семантический роутер, трёхуровневая память, онтология | PostgreSQL + pgvector | 274 |
| [`agentic_workflow_os`](agentic_workflow_os/) | Сама среда исполнения: роли Исполнитель/Критик/Контролёр, общая доска, Human-in-the-Loop, аудит | нет (stdlib) | 493 |
| [`saps`](saps/) | Прикладная система: подготовка требований лётной годности, интеллектуальный фронтенд к Teamcenter | PostgreSQL + pgvector, PDF-движок | 638 |

Итого 2301 проверка. Все проходят; числа выше проверены запуском, а не
переписаны из документации.

---

## С чего начать

**Просто посмотреть, как работает** — без ключей, баз и настройки:

```bash
cd agentic_workflow_os && make demo    # среда: цикл качества на офлайн-модели
cd saps && make demo                   # сертификация: PDF -> база -> агенты -> протокол
```

**Разобраться в устройстве** — у каждого проекта свой README и, где есть
что объяснять, `ARCHITECTURE.md` с разбором принятых решений и честным
списком ограничений.

**Запустить тесты:**

```bash
cd <проект> && make test
```

Тесты нигде не требуют сети и ключей. Там, где нужна база, используется
embedded PostgreSQL (`pgserver`); если его нет — соответствующие наборы
корректно пропускаются с указанием причины, а не падают.

## Как проекты соотносятся

Это не версии одного и того же и не слои одной системы. Разные задачи:

```
agent_system                 ОДИН агент. Дай задачу — сделает сам,
                             инструментами, с проверкой результата.

multi_agent_system_ontology  НЕСКОЛЬКО агентов-личностей. Кто ответит —
                             решает семантический роутер по смыслу
                             запроса, а не человек и не «мета-агент».

agentic_workflow_os          СРЕДА, в которой агенты живут. Не знает про
                             предметную область: роли, доска, точки
                             контроля, журнал. Специализация — JSON-файл.

saps                         ПРИКЛАДНАЯ система на этих идеях. Знает про
                             АП-25, MoC, Teamcenter и цену ошибки в
                             сертификации.
```

Порядок появления — слева направо; каждый следующий переосмысливает
предыдущий, а не наследует его код.

## Общая философия

Пять принципов, которым следуют все четыре проекта. Они не декларации —
под каждым есть код и тесты.

**1. Нет «агента над агентами».** Последовательность шагов задаёт
человек — списком в конфиге или JSON-определением. Модель решает, ЧТО
написать внутри шага; она не решает, какой шаг следующий, кто его
выполнит и какие инструменты ему доступны. Причина практическая:
конвейер, который вчера сделал одно, а сегодня другое на тех же данных,
невозможно сопровождать и не за что отвечать перед заказчиком.

**2. Решение принимает человек.** Особенно там, где цена ошибки высока.
В САПС агент не меняет требование, а готовит предложение с diff
«было/стало»; в AWOS пауза на человеке — состояние в базе, переживающее
перезапуск процесса.

**3. Зависимостей столько, сколько необходимо.** Два проекта работают на
голой стандартной библиотеке. Там, где зависимость обоснована
(PostgreSQL+pgvector для векторного поиска, PDF-движок для бинарного
формата), она обязательна и названа явно; остальное — ленивые импорты,
отсутствие которых не ломает систему, а даёт понятное сообщение.

**4. Детерминированное ядро, модель по краям.** Всё, что можно проверить
правилами, проверяется правилами: результат воспроизводим, объясним и
бесплатен. Модель подключается там, где нужен естественный язык.

**5. Тесты на реальной инфраструктуре.** Настоящий SQLite и PostgreSQL,
настоящие сокеты, настоящие подпроцессы. Заглушка ровно одна — на месте
самой LLM. Негативных сценариев больше, чем позитивных: ценность системы
в том, как она ведёт себя со сломанным ответом модели, недоступным
сервером и попыткой выйти за пределы рабочей папки.

## Требования

Python 3.10+. Всё остальное — по проектам:

| Нужно | Кому | Зачем |
|---|---|---|
| PostgreSQL 14+ с `pgvector` | MAOS, САПС | векторный поиск, общая база для нескольких процессов |
| `pymupdf` или `pypdf` | САПС | чтение PDF (бинарный формат, stdlib не справится) |
| `pgserver` | тесты MAOS и САПС | embedded PostgreSQL, чтобы тесты шли без развёрнутого сервера |
| опциональные пакеты | agent_system | навыки pdf/docparse/office/pg_ontology, см. `requirements-optional.txt` |

Языковая модель нигде не обязательна для запуска: у каждого проекта есть
офлайн-режим (детерминированная заглушка или правила без модели), на
котором проходят все тесты и работают демонстрации.
